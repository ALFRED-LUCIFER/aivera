# Aivera infrastructure (Bicep)

The dev environment lives inside Medvya's dev resource group `rg-medvya-dev-in` (Subscription 1, Central India) and holds synthetic data only ([ADR-008](../docs/adr/ADR-008-dev-environment-shares-medvya-dev.md)). The one exception is the AI resource, which sits in Aivera's own group `rg-aivera-ai-dev` in UAE North ([ADR-011](../docs/adr/ADR-011-dev-ai-in-uae-north-global.md)). Pilot and production are separate, in UAE North, and come with the launch epic AIV-P5-E03 (#34).

`main.bicep` is deployed at resource-group scope. Modules live in `modules/`, one per ticket.

Every Aivera resource is tagged `product=aivera`, `env=dev`, `data=synthetic`.

**Own Key Vault rather than an `aivera-` prefix in `kv-medvya-dev-3afs7i`:** a vault boundary keeps Aivera's identity scoped to Aivera's secrets with one role assignment, and a vault costs about $0 at dev volumes.

**Two identities rather than one:** PostgreSQL maps one Entra identity to one role, and the server has password sign-in off. With one identity the web app could sign in as the migrator, run DDL and switch row-level security off (AGENTS.md 1.4). The CI/CD identity also carries the GitHub federated credential, so a compromised web app cannot deploy.

### Web: what is not here, and why

- **Public, with sign-in.** The default address `https://ca-aivera-web-dev.<cae-aivera-dev domain>` is public over HTTPS only; `/app` needs a session from the dev External ID tenant ([recruiter sign-in runbook](../docs/runbooks/recruiter-sign-in.md)), and `/candidates/me` a candidate session once `entraCandidateClientId` is set ([candidate sign-in runbook](../docs/runbooks/candidate-sign-in.md)). Dev holds synthetic data only.
- shortcut: no Front Door, no custom domain and no portfolio subdomains in dev; they come with the launch epic AIV-P5-E03 (#34).

## Apply (owner only)

Agents never apply infrastructure (CLAUDE.md 7). Sign in with MFA first: `az login`, then `az account set -s "Subscription 1"`. Once, before the first apply that includes the AI resource: `az provider register -n Microsoft.CognitiveServices --wait` and `az group create -n rg-aivera-ai-dev -l uaenorth --tags product=aivera env=dev data=synthetic`. The deployment stays `-g rg-medvya-dev-in`; only the AI module deploys into the other group.

```sh
az deployment group what-if -g rg-medvya-dev-in -n aivera-dev --mode Incremental -f infra/main.bicep -p imageTag=<sha> alertEmail=<team address>
az deployment group create  -g rg-medvya-dev-in -n aivera-dev --mode Incremental -f infra/main.bicep -p imageTag=<sha> alertEmail=<team address>
```

Always `--mode Incremental` (the default, written out on purpose): the resource group is Medvya's, and Complete mode would delete every Medvya resource the template does not declare.

`imageTag` is the commit SHA of images already pushed to ghcr.io by `deploy-dev.yml`. On a later run, pass the tag running now so nothing moves: `az containerapp job show -g rg-medvya-dev-in -n job-aivera-migrate-dev --query 'properties.template.containers[0].image' -o tsv`. A second `create` with the same parameters changes nothing (the what-if shows no changes).

The `aivera` database already exists: it was created on 18 Nov 2026 with charset `UTF8` and collation `en_US.utf8`, the same values `modules/database.bicep` declares, so the deployment leaves it unchanged (the what-if should show no change to it).

### First deploy, in order

1. Merge the stack. `deploy-dev.yml` runs on `main` and pushes `ghcr.io/alfred-lucifer/aivera/web:<sha>` and `…/migrate:<sha>`; its deploy job is skipped because the repository variables are not set yet.
2. Make both packages public, once (GitHub, Packages, each package's settings, Change visibility). The repository is public, so the images reveal nothing new, and the apps then pull without a registry secret.
3. `az deployment group create -g rg-medvya-dev-in -n aivera-dev --mode Incremental -f infra/main.bicep -p imageTag=<sha from step 1> alertEmail=<team address>` (also creates the subnet `snet-aivera-dev` and the environment `cae-aivera-dev`). The `aivera` database was already created on 18 Nov 2026; the deployment leaves it unchanged.
4. `sh infra/scripts/bootstrap-db.sh` (below).
5. Set the repository variables from the deployment outputs and the account (`gh variable set AZURE_CLIENT_ID -b <cicdIdentityClientId>`, the same for `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`).
6. Re-run `deploy-dev` (`gh workflow run deploy-dev.yml`). It migrates, deploys web, smoke-tests the public URL from the runner and rolls back the image on failure or cancellation.
7. Optional, for the live AI eval (AIV-P0-029): create the GitHub environment `ai-eval` and limit its deployment branches to `main` (the identity trusts the environment, so this is what keeps other branches out; the workflow also runs the live job only on `main` and manual runs), then `gh variable set AI_EVAL_CLIENT_ID -b <aiEvalIdentityClientId>` and `gh variable set AI_EVAL_RESOURCE_NAME -b <aiResourceName>`. Until `AI_EVAL_CLIENT_ID` is set, `ai-eval.yml` scores the recorded answers only. Spend is bounded twice: `liveTokenCap` per run in code, and the `gpt-main` deployment's 100k tokens per minute in `ai.bicep`, which no workflow can raise.

**Migrations must be expand-only (backward-compatible).** A rollback restores the previous web image over the already-migrated schema, so the old code must still work against it. Contract steps (drop, rename, narrow) ship in a later release, once no running image needs the old shape (ADR-004).

### Database roles (once, after the first `create`)

The server has password sign-in off and no public access, so the roles are created from inside the VNet by a server Entra admin (the owner):

```sh
sh infra/scripts/bootstrap-db.sh
```

It borrows one execution of `job-aivera-migrate-dev` with a `postgres:16-alpine` container and the owner's own short-lived Entra token (held in a job secret for the length of the execution and removed when it ends, never in the execution template), connects with `sslmode=verify-full`, runs `infra/sql/bootstrap-roles.sql`, and prints each role's flags and the databases it can connect to. Expect `rolsuper`, `rolbypassrls` and `rolcreaterole` false for all four roles. Rerun it after the apply that adds `id-aivera-relay-dev` (AIV-P0-014) and before the next deploy: the candidates outbox migration names `aivera_relay`, so the migrate job fails until the role exists. If `can_connect_to` lists `medvya`, Medvya's database still grants `CONNECT` to `PUBLIC`: agree with Medvya to revoke it (ADR-008). Rerunning is safe.

**AIV-P3-002 added `aivera_public`** (no login, entered by `aivera_app` with `SET LOCAL ROLE` for the candidate site's public job reads). On a server bootstrapped before it, rerun the script once, then run the migration job so the migrator grants the role its columns (`modules/jobs/src/infrastructure/grants.sql`, re-applied on every migrate):

```sh
sh infra/scripts/bootstrap-db.sh
az containerapp job start -g rg-medvya-dev-in -n job-aivera-migrate-dev
```

Until both have run, the public job pages on Azure dev show their "could not load" state; nothing else is affected.

The roles are mapped to the identities' object ids. If `id-aivera-dev`, `id-aivera-cicd-dev` or `id-aivera-relay-dev` is ever deleted and recreated, its new object id no longer matches: drop the stale role (`DROP ROLE aivera_app` after reassigning what it owns) and rerun the script.

### pgvector (AIV-P0-030, not now)

The shared server's `azure.extensions` allows `PGCRYPTO,PG_STAT_STATEMENTS,PGAUDIT,PG_TRGM`. Before the first migration that needs `vector`, the owner adds it, keeping Medvya's entries (it is a dynamic parameter, no restart):

```sh
az postgres flexible-server parameter set -g rg-medvya-dev-in -s psql-medvya-dev-3afs7i \
  -n azure.extensions -v PGCRYPTO,PG_STAT_STATEMENTS,PGAUDIT,PG_TRGM,VECTOR
```

### Medvya's VNet and the new subnet

The subnet is the only change inside a Medvya resource. If Medvya's own infrastructure code ever redeploys `vnet-medvya-dev-3afs7i` with its subnets declared inline, that deployment would try to remove `snet-aivera-dev` (and fail while the environment uses it). Tell Medvya to declare its subnets as child resources, or to add `snet-aivera-dev` to its template.

CI builds and lints the Bicep on every pull request (`pr.yml`, step `bicep`); any linter warning fails it.
