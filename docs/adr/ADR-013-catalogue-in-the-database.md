# ADR-013: The catalogue in the database, with draft and published versions

- **Status:** Proposed, 20 Nov 2026. Points marked "proposed, owner to confirm" are listed under "Open for the owner"
- **Ticket:** AIV-P2-042, for epic AIV-P2-E08 (build: AIV-P2-043 to 050)
- **Amends:** [ADR-012](ADR-012-operator-console.md): operators may now change the catalogue, only as described here. Who is an operator is unchanged.

## Context

The catalogue is code today. `modules/jobs/src/domain/job-types.ts` holds the ten job types, each with its "Evidence that counts" text and four starter competencies (`JOB_TYPE_CATALOGUE_VERSION`). `modules/jobs/src/domain/domain-packs.ts` holds the 8 domain packs, their competencies and their regional hints for the UAE, KSA and India (`DOMAIN_PACK_CATALOGUE_VERSION`). Labels are `jobTypes.*` and `domainPacks.*` keys in `en.json`. Database check constraints list the keys: `competency_pack_key_check` and `job_type_check` in `jobs`, `account_work_type_check` in `candidate-accounts`. Adding a pack or a job type therefore needs a code PR and a migration.

The catalogue reaches recruiters and the AI. Add a job seeds starter competencies and offers pack suggestions. `jobs.detectDomain` gets the pack keys and regions as the enum of its output schema (`detectDomainRequest(input, { domains, regions }, sources)`). `jobs.draftCompetencies` drafts against the job type. A kept pack competency stores `pack_key` and `pack_version`. The marketing page, the candidate sign-up work type and the workspace hiring focus read the job types.

Owner decision of 20 Nov 2026: the catalogue (job types, domain packs and their competencies, regional hints) moves into PostgreSQL so that platform operators can add, edit and retire entries at `/ops/catalogue`. An edit changes what every recruiter is offered and what the model can detect, so it must not weaken the human-decision, evidence and fairness rules (AGENTS.md 1.5, 1.6) or the eval rule (AGENTS.md 3.12, [ADR-006](ADR-006-ai-on-azure-foundry.md) point 8).

## Decision

1. **Tables in the `jobs` schema.** `jobs` owns the catalogue ([modules](../02-architecture/modules.md)). `catalogue_version` holds the version number, status `draft | published`, created by, published by, published at, the reason and the content hash. Per version, child tables hold the job types (key, position, labels, evidence text, four starters, retired flag), the packs (key, labels, retired), the pack competencies (name, meaning, evidence, levels 1/3/5, applies-to job types, core job types, level needed, type, retired) and the regional hints (pack, region, the same fields without core). Forward-only Drizzle Kit migrations ([ADR-004](ADR-004-database-and-migrations.md)).
2. **Platform tables.** The catalogue holds no workspace data, no candidate data and no personal data, only operators' opaque user ids. So the tables have no `workspace_id` and no tenant policy, like `audit.platform_entry` ([ADR-005](ADR-005-workspace-tenancy.md), ADR-012 point 8). The tenancy suite (`tests/integration/src/tenancy.test.ts`) lists each one as a platform table with that reason.
3. **Versions.** One version number covers the whole catalogue and replaces `JOB_TYPE_CATALOGUE_VERSION` and `DOMAIN_PACK_CATALOGUE_VERSION` (proposed, owner to confirm). A draft starts as a copy of the latest published version. At most one draft is open at a time (partial unique index on `status = 'draft'`). Both operators edit the same draft, and each save carries the draft's revision, so a stale save is refused rather than overwriting another operator's edit.
4. **Published versions are immutable.** A trigger refuses `UPDATE` and `DELETE` on a published version's rows, in every catalogue table, for every role, the migration owner included. Changing a published entry means publishing a new version. A draft is referenced by nothing, so discarding it deletes its rows.
5. **Keys.** Lower snake case, `^[a-z][a-z0-9_]{2,47}$`, enforced by a check constraint and unique per version. A key is fixed once published and never renamed or reused. An entry new in a draft may change its key until publish.
6. **Retire, never delete.** An entry from a published version is retired in the next version, never removed: a kept rubric competency references its pack (`jobs.competency.pack_key` and `pack_version`), and jobs, workspace hiring focus and candidate work types store job type keys. Retired entries stay readable so kept competencies and old jobs still show their labels. Add a job, the sign-up pickers and the pack suggestions never offer a retired entry.
7. **Validation without foreign keys.** `competency_pack_key_check`, `job_type_check` and the candidate-accounts `work_type` enum (`account_work_type_check`) are replaced by the key format check. The application validates a key against the published catalogue through the `jobs` contract at every trust boundary (zod, AGENTS.md 3.7): a retired key is accepted on existing rows and refused for new ones. Cross-module references stay opaque keys, never foreign keys (AGENTS.md 3.3). `competency_domain_pack_check` stays.
8. **Rubrics keep the version that seeded them.** A kept pack competency records the catalogue version that seeded it (`pack_version`). Starter and pack text is copied into the rubric when the recruiter keeps it. Publishing never touches a job, a rubric, a competency or a score. Catalogue entries are suggestions: the recruiter keeps, edits or removes each one, and the hiring owner approves the rubric (AGENTS.md 1.5).
9. **Seed.** Today's code catalogue becomes published version 1 in a Drizzle Kit custom migration, generated from the code by a script in `tools/` and committed: `insert … on conflict do nothing`, so running it twice changes nothing. Published by the system actor `system:seed` with the reason "Catalogue version 1 from code (AIV-P1-004, AIV-P1-061)". A snapshot test proves version 1 equals the code catalogue field for field, so dev, CI and the pilot start identical (AIV-P2-043). The code catalogue is deleted when readers switch (AIV-P2-044).
10. **Labels per locale** (proposed, owner to confirm). Each entry stores its label text per locale in its row: `en` required, `ar` optional until the recruiter app ships in Arabic (AIV-P5-009). The seed copies today's `jobTypes.*` and `domainPacks.*` English text from `en.json`. Those keys leave `en.json` when readers switch. Competency and hint text is already stored English seed text (the existing `shortcut:` in `domain-packs.ts`).
11. **Fairness on save** (rule list proposed, owner to confirm). A competency, starter or regional hint is a skill shown with evidence. It is never an employer, a nationality, a region of origin, a residency or "worked at X" (epic #290, AGENTS.md 1.5, 1.6). The application refuses a save when the evidence is empty, or when the name or meaning matches a deterministic rule list in the `jobs` domain: "worked at", "years at", "ex-" an employer, "nationals", "national", "citizen", "native", "resident of", "residence visa", "born in", "from <country>", and listed company names. The refusal names the rule; logs never carry the matched text. Type is always `desirable`: the catalogue cannot make a competency or a regional hint mandatory, and the server refuses a request that tries. Only the recruiter can raise a kept competency, and the hiring owner approves it.
12. **Eval gate** (proposed, owner to confirm). Pack keys feed `jobs.detectDomain` and the pack suggestions, so a catalogue change is a change to what the AI sees and is evaluated like one:
    - The prompt text and its version stay in code. The catalogue goes to the prompt as data, as it does today.
    - **Publish is refused until an eval run for that draft's content hash passed.** A worker job (AIV-P2-048) runs the `jobs.detectDomain` and `jobs.draftCompetencies` golden sets live against the environment's AI deployment, with the draft catalogue as data, through `@aivera/ai`, under the existing thresholds and hard gates in `packages/ai/evals/config.ts`. It stores the result against the content hash (a hash of the draft's entries in a canonical order). Any edit after the run changes the hash, and the run no longer counts.
    - **A draft that adds a pack key cannot publish until golden cases cover that key.** They are added in code, in `packages/ai/evals/jobs.detectDomain/`, by a reviewed PR, synthetic only (AGENTS.md 1.1). Until then the run fails with the missing key named.
    - A draft that only changes labels or retires an entry still needs a passing run. It is cheap and keeps one rule.
    - Inputs are the synthetic golden cases only, never a workspace's job description or a candidate's data. Token use counts against a platform eval budget, not a workspace's.
    - Rejected: operator-written eval cases stored with the draft. Operators would paste real job descriptions, and real names or employers would enter an eval set (AGENTS.md 1.1).
    - Rejected: no eval on catalogue changes. A changed enum or competency can silently drop domain accuracy or fairness below its threshold, with every recruiter's suggestions affected.
13. **Publish.** "Review and publish" shows every change against the latest published version on the shared preview-confirm card (added, edited with before and after, retired; "Nothing changes until you confirm."). Publish needs a passed eval for the current content hash, a reason of at least 10 characters and at least one change. It runs in one serializable transaction: the draft becomes published version N with its publisher, time and reason, and a racing edit or publish makes it fail with nothing changed. There is no rollback: to undo a change, publish a new version that reverts it, through the same gate (proposed, owner to confirm).
14. **Audit.** Every draft change goes to `audit.platform_entry` with the operator's user id and the version id: `catalogue.draft_opened`, `catalogue.entry_added`, `catalogue.entry_edited`, `catalogue.entry_retired`, `catalogue.entry_removed` (an entry new in the draft), `catalogue.draft_discarded`, `catalogue.eval_requested` and `catalogue.published` (with the reason and change counts). Each is the last statement in its transaction (AGENTS.md 3.6).
15. **Reads.** Recruiters' Add a job, the marketing page, the candidate sign-up, the workspace sign-up, the seed and the AI calls read only the latest published version, through a `jobs` contract method. Published versions never change, so a process may cache a version by its number. Only `/ops` reads drafts, through contract methods on the ops allow-list (ADR-012 point 6), each awaiting `platformOperator()`.
16. **What stays fixed.**
    - Regions stay `uae`, `ksa` and `india`. A new region touches data residency and market rules, so it needs its own ADR (proposed, owner to confirm).
    - Job types carry no stages. Job stages stay the fixed `defining_rubric → collecting_evidence → round_1 → decision → closed` (proposed, owner to confirm).
    - Operators are configured only through the Key Vault secret `platform-operator-emails` (ADR-012 point 1, unchanged). Nothing about the catalogue widens what operators can see (ADR-012 point 7).

## Consequences

- Operators can add a job type, a pack, a competency or a regional hint without a code change, except that a new pack key needs golden cases in a reviewed PR before it can publish.
- Recruiters see no change until a version is published. Version 1 equals today's catalogue, so switching readers changes nothing on screen.
- Three check constraints become a key format check plus application validation through the `jobs` contract. Validation of keys therefore rests on the contract, not on the database, as it does for every cross-module reference.
- The code catalogue constants (`JOB_TYPES`, `JOB_TYPE_CATALOGUE`, `DOMAIN_KEYS`, `listDomainPacks`, `getDomainPack`, both version constants) and the `jobTypes.*` and `domainPacks.*` message keys are removed in AIV-P2-044. Pure helpers (`nameKey`, the per-job-type pack view, `isRegionalHint`) take a catalogue value as input.
- `packages/ai/evals/config.ts` drops the hard-coded `domainCatalogue`. CI's eval run reads the catalogue snapshot committed with AIV-P2-043, and its drift test compares against that snapshot. The draft gate (point 12) evaluates each later version live before it publishes.
- Each publish costs one live eval run's tokens (capped by `liveTokenCap`) against the platform budget.
- The console's read-only catalogue copy ("The catalogue changes only through a reviewed pull request.", AIV-P5-015) is replaced when the editor ships (AIV-P2-045).
- The tenancy suite lists every catalogue table as a platform table with its reason. Tenant policies, `FORCE ROW LEVEL SECURITY` and roles are unchanged.

## Open for the owner

The owner decided the move, draft and publish with a reason, audit, immutable published versions, rubrics keeping their seeding version and operators from Key Vault only. These points are proposed and need the owner's confirmation before AIV-P2-043 starts:

1. The eval gate (point 12): publish refused until a live eval run for the draft's content hash passes the `jobs.detectDomain` and `jobs.draftCompetencies` golden sets, including drafts that only change labels or retire an entry.
2. A new pack key needs golden cases added in a reviewed code PR before it can publish (point 12).
3. Labels stored per locale in the catalogue rows, English required (point 10).
4. The fairness refused-wording list (point 11).
5. No rollback: revert by publishing a new version (point 13).
6. One version number for the whole catalogue (point 3).
7. Regions fixed to the UAE, KSA and India; a new one needs its own ADR (point 16).
8. Job types carry no stages (point 16).
