# ADR-013: The catalogue in the database, with draft and published versions

- **Status:** Accepted, 20 Nov 2026. The owner confirmed the eval gate, labels per locale, the fairness list, no rollback and no stages, and decided that regions are open worldwide (point 16).
- **Ticket:** AIV-P2-042, for epic AIV-P2-E08 (build: AIV-P2-043 to 050)
- **Amends:** [ADR-012](ADR-012-operator-console.md): operators may now change the catalogue, only as described here. Who is an operator is unchanged. [ADR-006](ADR-006-ai-on-azure-foundry.md) point 8: a worker job may run the live eval for a catalogue draft (point 12), besides the `ai-eval-live` CI job.

## Context

The catalogue is code today. `modules/jobs/src/domain/job-types.ts` holds the 10 job types, each with its "Evidence that counts" text and four starter competencies (`JOB_TYPE_CATALOGUE_VERSION`). `modules/jobs/src/domain/domain-packs.ts` holds the 8 domain packs, their competencies and their regional hints for the UAE, KSA and India (`DOMAIN_PACK_CATALOGUE_VERSION`). Labels are `jobTypes.*` and `domainPacks.*` keys in `en.json`. Database check constraints list the keys: `competency_pack_key_check` and `job_type_check` in `jobs`, `account_work_type_check` in `candidate-accounts`. Adding a pack or a job type therefore needs a code PR and a migration.

The catalogue reaches recruiters and the AI. Add a job seeds starter competencies and offers pack suggestions. `jobs.detectDomain` gets the pack keys and regions as the enum of its output schema (`detectDomainRequest(input, { domains, regions }, sources)`). `jobs.draftCompetencies` drafts against the job type. A kept pack competency stores `pack_key` and `pack_version`. The marketing page, the candidate sign-up work type and the workspace hiring focus read the job types.

Owner decision of 20 Nov 2026: the catalogue (job types, domain packs and their competencies, regional hints) moves into PostgreSQL so that platform operators can add, edit and retire entries at `/ops/catalogue`. An edit changes what every recruiter is offered and what the model can detect, so it must not weaken the human-decision, evidence and fairness rules (AGENTS.md 1.5, 1.6) or the eval rule (AGENTS.md 3.12, [ADR-006](ADR-006-ai-on-azure-foundry.md) point 8).

## Decision

1. **Tables in the `jobs` schema.** `jobs` owns the catalogue ([modules](../02-architecture/modules.md)). `catalogue_version` holds the version number, status `draft | published`, created by, published by, published at, the reason and the content hash. Per version, child tables hold the job types (key, position, labels, evidence text, four starters, retired flag), the packs (key, labels, retired), the pack competencies (name, meaning, evidence, levels 1/3/5, applies-to job types, core job types, level needed, type, retired) and the regional hints (pack, region, the same fields without core). Forward-only Drizzle Kit migrations ([ADR-004](ADR-004-database-and-migrations.md)).
2. **Platform tables.** The catalogue holds no workspace data, no candidate data and no personal data: its actor columns hold an operator's opaque user id or the system actor `system:seed`. So the tables have no `workspace_id` and no tenant policy, like `audit.platform_entry` ([ADR-005](ADR-005-workspace-tenancy.md), ADR-012 point 8). The tenancy suite (`tests/integration/src/tenancy.test.ts`) lists each one as a platform table with that reason.
3. **Versions.** One version number covers the whole catalogue and replaces `JOB_TYPE_CATALOGUE_VERSION` and `DOMAIN_PACK_CATALOGUE_VERSION`. A draft starts as a copy of the latest published version. At most one draft is open at a time (partial unique index on `status = 'draft'`). Every operator edits the same draft, and each save carries the draft's revision, so a stale save is refused rather than overwriting another operator's edit.
4. **Published versions are immutable.** A trigger refuses `UPDATE` and `DELETE` on a published version's rows, in every catalogue table, for every role, the migration owner included. Changing a published entry means publishing a new version. A draft is referenced by nothing, so discarding it deletes its rows.
5. **Keys.** Lower snake case, `^[a-z][a-z0-9_]{2,47}$`, enforced by a check constraint and unique per version. The keys `none` (the "no clear domain" answer of `jobs.detectDomain`), `several` and `other` (the hiring-focus catch-alls) are reserved and refused. A key is fixed once published and never renamed or reused. An entry new in a draft may change its key until publish.
6. **Retire, never delete.** An entry from a published version is retired in the next version, never removed: a kept rubric competency references its pack (`jobs.competency.pack_key` and `pack_version`), and jobs (`jobs.job` and `jobs.public_job`), workspace hiring focus and candidate work types store job type keys. Retired entries stay readable so kept competencies and old jobs still show their labels. Add a job, the sign-up pickers and the pack suggestions never offer a retired entry.
7. **Validation without foreign keys.** `competency_pack_key_check`, `job_type_check` and the candidate-accounts `work_type` enum (`account_work_type_check`) are replaced by the key format check. The application validates a key against the published catalogue through the `jobs` contract at every trust boundary (zod, AGENTS.md 3.7): a retired key is accepted on existing rows and refused for new ones. Cross-module references stay opaque keys, never foreign keys (AGENTS.md 3.3). `competency_domain_pack_check` stays.
8. **Rubrics keep the version that seeded them.** A kept pack competency records the catalogue version that seeded it (`pack_version`). Starter and pack text is copied into the rubric when the recruiter keeps it. Publishing never touches a job, a rubric, a competency or a score. Catalogue entries are suggestions: the recruiter keeps, edits or removes each one, and the hiring owner approves the rubric (AGENTS.md 1.5).
9. **Seed.** Today's code catalogue becomes published version 1 in a Drizzle Kit custom migration, generated from the code by a script in `tools/` and committed: `insert … on conflict do nothing`, so running it twice changes nothing. Published by the system actor `system:seed` with the reason "Catalogue version 1 from code (AIV-P1-004, AIV-P1-061)". A snapshot test proves version 1 equals the code catalogue field for field, so dev, CI and the pilot start identical (AIV-P2-043). The code catalogue is deleted when readers switch (AIV-P2-044).
10. **Labels per locale**. Each entry stores its label text per locale in its row: `en` required, `ar` optional until the recruiter app ships in Arabic (AIV-P5-009). The seed copies today's `jobTypes.*` and `domainPacks.*` English text from `en.json`. Those keys leave `en.json` when readers switch. Competency and hint text is already stored English seed text (the existing `shortcut:` in `domain-packs.ts`).
11. **Fairness on save**. A competency, starter or regional hint is a skill shown with evidence. It is never an employer, a nationality, a region of origin, a residency or "worked at X" (epic #290, AGENTS.md 1.5, 1.6). The application refuses a save when the evidence is empty, or when the name or meaning matches a deterministic rule list in the `jobs` domain. Rules match whole words and phrases, never substrings: "worked at", "years at", "ex-" followed by an employer, "nationals", "<country> national", "citizen", "native speaker", "resident of", "residence visa", "born in", "from <country>", and listed company names. A bare "national" or "native" is not a rule, because version 1 rightly holds "National digital identity sign-in", "international card payments" and "cloud-native". A test runs the rule list against version 1 and must find nothing, so seeded entries stay editable. The refusal names the rule; logs never carry the matched text. Type is always `desirable`: the catalogue cannot make a competency or a regional hint mandatory, and the server refuses a request that tries. Only the recruiter can raise a kept competency, and the hiring owner approves it.
12. **Eval gate**. Pack keys feed `jobs.detectDomain` and the pack suggestions, so a catalogue change is a change to what the AI sees and is evaluated like one:
    - The prompt text and its version stay in code. The catalogue goes to the prompt as data, as it does today. Since the output enum now changes with each published version, every `jobs.detectDomain` and `jobs.draftCompetencies` call records the catalogue version next to the prompt version, in telemetry and on the stored suggestion (AGENTS.md 3.12).
    - **Publish is refused until an eval run for that draft's content hash passed.** A worker job (AIV-P2-048) runs the `jobs.detectDomain` and `jobs.draftCompetencies` golden sets live against the environment's AI deployment, with the draft catalogue as data, through `@credalent/ai`, under the existing thresholds and hard gates in `packages/ai/evals/config.ts`. It stores the result against the content hash (a hash of the draft's entries in a canonical order). Any edit after the run changes the hash, and the run no longer counts.
    - **A draft that adds a pack key cannot publish until golden cases cover that key.** They are added in code, in `packages/ai/evals/jobs.detectDomain/`, by a reviewed PR, synthetic only (AGENTS.md 1.1). Until then the run fails with the missing key named.
    - A draft that only changes labels or retires an entry still needs a passing run. It is cheap and keeps one rule.
    - This amends ADR-006 point 8, which runs live evals only in the `ai-eval-live` CI job. The worker runs the draft eval in its own environment (dev: Central India calling `gpt-main`, [ADR-011](ADR-011-dev-ai-in-uae-north-global.md); pilot: UAE North) with the worker's managed identity, granted Cognitive Services OpenAI User on that environment's AI account only. Today only the web app's identity has that role (ADR-011 point 3); AIV-P2-048 adds the worker's grant in Bicep, applied by the owner. Inputs are the synthetic golden cases only, never a workspace's job description or a candidate's data, so the run is safe in the pilot environment too.
    - Token use counts against a platform eval budget, not a workspace's. The AI client counts tokens per workspace today (ADR-006 point 2), so AIV-P2-048 builds that budget: a reserved platform budget key in the token budget store, capped per run by `liveTokenCap` and per day by a platform limit. **Amended in AIV-P2-048:** the budget is counted in `jobs.catalogue_eval_run` (each run's tokens), not in the token budget store, whose rows belong to a workspace by foreign key; each run's client gets a budget of `liveTokenCap` or what is left of `EVAL_DAILY_TOKEN_CAP` (1,500,000) today, whichever is lower. The worker already signs in with the app identity, which holds the AI role, so no new grant was needed; the new `jobs` queue is in `infra/modules/messaging.bicep`. The request writes `CatalogueEvalRequested.v1` to `jobs.outbox` and the worker records it in `jobs.inbox`; both tables carry the tenant policy (ADR-005), so the eval's rows carry a fixed synthetic workspace id, `CATALOGUE_EVAL_SCOPE`, that no real workspace has, and its transactions run in that scope. This keeps the outbox and inbox policies unchanged rather than adding a platform exception to them; the scope reaches no workspace's rows, and the catalogue tables have no tenant policy. The worker maps the event to the `jobs` queue only with `CATALOGUE_EVAL=on`, set by the same Bicep apply that creates the queue: mapped to a missing queue, each refused send would hold back the rest of `jobs.outbox` (`RubricApproved.v1` included), while an unmapped type fails alone. As the product prompts stand, only the pack and region keys reach the model (`jobs.draftCompetencies` takes no catalogue data), so the gate tells for packs or regions added, retired or renamed, not for label or competency edits (a `shortcut:` in `packages/ai/evals/catalogue.ts`).
    - Rejected: operator-written eval cases stored with the draft. Operators would paste real job descriptions, and real names or employers would enter an eval set (AGENTS.md 1.1).
    - Rejected: no eval on catalogue changes. A changed enum or competency can silently drop domain accuracy or fairness below its threshold, with every recruiter's suggestions affected.
13. **Publish.** "Review and publish" shows every change against the latest published version on the shared preview-confirm card (added, edited with before and after, retired; "Nothing changes until you confirm."). Publish needs a passed eval for the current content hash, a reason of at least 10 characters and at least one change. It runs in one serializable transaction: the draft becomes published version N with its publisher, time and reason, and a racing edit or publish makes it fail with nothing changed. There is no rollback: to undo a change, publish a new version that reverts it, through the same gate. As built (AIV-P2-049): every draft write, eval request, publish and discard first locks the one draft row (`SELECT … FOR UPDATE`) and names the revision it read, which orders them as a serializable transaction would: the second finds the draft moved on (`stale`, or `no_draft` after a publish) and changes nothing. Publish is one update of that row, and readers take the newest published version, so they switch at commit. The content hash stays on the eval run (`catalogue_eval_run.content_hash`), not on `catalogue_version`; the INSERT shortcut of migration 0016 stays until a later ticket stores it there.
14. **Audit.** Every draft change goes to `audit.platform_entry` with the operator's user id and the version id: `catalogue.draft_opened`, `catalogue.entry_added`, `catalogue.entry_edited`, `catalogue.entry_retired`, `catalogue.entry_removed` (an entry new in the draft), `catalogue.draft_discarded`, `catalogue.eval_requested` and `catalogue.published` (with the reason and change counts). Each is the last statement in its transaction (AGENTS.md 3.6). AIV-P2-043 adds these actions to `platform_entry_action_check` in an `audit` migration.
15. **Reads.** Recruiters' Add a job, the marketing page, the candidate sign-up, the workspace sign-up, the seed and the AI calls read only the latest published version, through a `jobs` contract method. Published versions never change, so a process may cache a version by its number. Only `/ops` reads drafts, through contract methods on the ops allow-list (ADR-012 point 6), each awaiting `platformOperator()`.
16. **Regions are catalogue data, open worldwide** (owner decision, 20 Nov 2026). The catalogue version holds a regions table (key, labels per locale, retired), seeded with `uae`, `ksa` and `india`; an operator may add any region in the world (a country or a named market such as "EU" or "GCC") in a draft, with its regional hints per pack. Region keys follow the pack key rules, except that they may be two letters ("eu", `^[a-z][a-z0-9_]{1,47}$`, migration 0023, AIV-P2-059): lower-case, unique in the version, changeable or removable only while new in the draft, never renamed once published, retired rather than deleted. A retired region's hints stay in the draft, read-only, and recruiters keep the region until publish. A region feeds `jobs.detectDomain`'s output enum like a pack key, so a draft that adds a region key cannot publish until golden cases cover it (point 12). A region here is a market whose regulation or practice a candidate can show skill in; it is never where a candidate lives or comes from (point 11), and it says nothing about where data is stored: data residency stays as AGENTS.md 1.10 and ADR-008 set it.
17. **What stays fixed.**
    - Job types carry no stages. Job stages stay the fixed `defining_rubric → collecting_evidence → round_1 → decision → closed`.
    - Operators are configured only through the Key Vault secret `platform-operator-emails` (ADR-012 point 1, unchanged). Nothing about the catalogue widens what operators can see (ADR-012 point 7).

## Consequences

- Operators can add a job type, a pack, a region, a competency or a regional hint without a code change, except that a new pack or region key needs golden cases in a reviewed PR before it can publish.
- Recruiters see no change until a version is published. Version 1 equals today's catalogue, so switching readers changes nothing on screen.
- Three check constraints become a key format check plus application validation through the `jobs` contract. Validation of keys therefore rests on the contract, not on the database, as it does for every cross-module reference.
- The code catalogue constants (`JOB_TYPES`, `JOB_TYPE_CATALOGUE`, `DOMAIN_KEYS`, `listDomainPacks`, `getDomainPack`, both version constants) and the `jobTypes.*` and `domainPacks.*` message keys are removed in AIV-P2-044, along with the Drizzle `{ enum: JOB_TYPES }` and `{ enum: DOMAIN_KEYS }` column types (`jobs.job`, `jobs.public_job`, `jobs.competency`, `candidate-accounts`), the `HIRING_FOCUS` list in `features/workspace-signup` and the catalogue lines of `modules/jobs/README.md`. Pure helpers (`nameKey`, the per-job-type pack view, `isRegionalHint`) take a catalogue value as input.
- `packages/ai/evals/config.ts` drops the hard-coded `domainCatalogue`. CI's eval run reads the catalogue snapshot committed with AIV-P2-043, and its drift test compares against that snapshot. The draft gate (point 12) evaluates each later version live before it publishes.
- Each publish costs one live eval run's tokens (capped by `liveTokenCap`) against the platform budget.
- The console's read-only catalogue copy ("The catalogue changes only through a reviewed pull request.", AIV-P5-015) is replaced when the editor ships (AIV-P2-045).
- The tenancy suite lists every catalogue table as a platform table with its reason. Tenant policies, `FORCE ROW LEVEL SECURITY` and roles are unchanged.

## Owner decisions (20 Nov 2026)

Confirmed as proposed: the eval gate on every draft, including label-only and retire-only drafts (point 12); golden cases in a code PR for a new pack or region key (points 12, 16); labels per locale with English required (point 10); the fairness rule list (point 11); no rollback (point 13); job types carry no stages (point 17). Changed: regions are not fixed; operators may add any region worldwide (point 16). One version number for the whole catalogue (point 3) is the design default; the owner did not object.
