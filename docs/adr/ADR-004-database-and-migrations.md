# ADR-004: PostgreSQL, Drizzle ORM and Drizzle Kit migrations, one schema per module

- **Status:** Accepted, 18 Nov 2026
- **Ticket:** AIV-P0-001 (decision), AIV-P0-002 (implementation)

## Context

Next.js has no database or migration system of its own. Medvya gave each module its own PostgreSQL schema and its own forward-only, reviewed migrations (EF Core). We need the same guarantees in TypeScript: a typed query layer, migrations a reviewer can read as SQL, and per-module ownership so parallel work on two modules never collides.

Options considered: Prisma (one schema file for the whole app, which works against per-module ownership; its own engine), Kysely + hand-written migrations (no schema-to-migration generation), Drizzle (TypeScript schemas, SQL migrations generated by Drizzle Kit, row-level security policies expressible in the schema, no engine binary).

## Decision

**Drizzle ORM** for queries and **Drizzle Kit** for migrations, on PostgreSQL 17 (Azure Flexible Server; Docker locally; Testcontainers in tests).

1. **One PostgreSQL schema per module**, named after the module (`jobs`, `evidence`…), declared with `pgSchema('<m>')` in `modules/<m>/src/infrastructure/schema.ts`.
2. **Per-module Drizzle Kit config** `modules/<m>/drizzle.config.ts`: `schema` → that module's `schema.ts`, `schemaFilter: ['<m>']`, `out` → `modules/<m>/src/infrastructure/migrations`, `migrations: { schema: '<m>', table: '__migrations' }`, `strict: true`, `verbose: true`.
3. **Generate, commit, review.** `pnpm db:generate` runs `drizzle-kit generate` for changed modules; the SQL files are committed and reviewed like code. **Forward-only:** never edit an applied migration; add a new one. Destructive changes (drop, rename, type narrowing) need expand → migrate data → contract across separate releases.
4. **Apply in order.** `pnpm db:migrate` runs the migration runner in `packages/db`, which applies each module's migrations with Drizzle's migrator in the order listed in `packages/db/src/modules.ts` (platform first: `audit`, `workspaces`; then the rest). In Azure it runs as a Container Apps job inside the virtual network before the new app revision takes traffic, with a migrator role that is not the app's role.
5. **`drizzle-kit push` is allowed only against a throwaway local database.** Never against a shared or cloud database.
6. **Cross-module references are opaque ids** (`uuid`), never foreign keys across schemas. Inside a module, foreign keys and check constraints are used freely.
7. **Row-level security is part of the schema** (`pgPolicy` in Drizzle) and its migration; see ADR-005.
8. **Roles:** `aivera_migrator` owns the schemas and runs migrations; `aivera_app` has DML only, is not the table owner, and is therefore subject to `FORCE ROW LEVEL SECURITY`.
9. Ids are UUIDv7 generated in the application. Timestamps are `timestamptz`. Money is `bigint` minor units plus a `char(3)` currency.

## Consequences

- Parallel agents working on different modules never touch the same migration folder; two PRs adding migrations to the same module are serialised (runbook: parallel agents).
- Reviewers read plain SQL. Integration tests run the real migrations on Testcontainers PostgreSQL, so a broken migration fails CI.
- An ERD is generated from the Drizzle schemas once the first module exists, with a CI staleness check.
