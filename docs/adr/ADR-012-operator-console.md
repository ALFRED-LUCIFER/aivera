# ADR-012: The operator console: who gets in, what it reads, how it is audited

- **Status:** Accepted, 19 Nov 2026 (point 10 open for the owner)
- **Ticket:** AIV-P2-035, for epic AIV-P2-E08 (AIV-P2-035 to 039, AIV-P5-015 to 018)
- **Amended by:** [ADR-013](ADR-013-catalogue-in-the-database.md) (proposed): operators edit the catalogue through a draft, an eval run and a published version; who is an operator is unchanged

## Context

The people who run Credalent need a console: workspaces, approvals, suspensions, AI budgets, catalogue, role requests, subscriptions and the deletion queue. They are not workspace admins, and they must never see candidate data.

Every workspace-owned table has a tenant policy on `app.workspace_id` with `FORCE ROW LEVEL SECURITY`, and no role may bypass it (AGENTS.md 1.4, [ADR-005](ADR-005-workspace-tenancy.md)). Dev shares Medvya's PostgreSQL server ([ADR-008](ADR-008-dev-environment-shares-medvya-dev.md)), where creating a role is a manual owner step (as it was for `aivera_public`). The console must not need one.

## Decision

1. **Who is an operator.** A person whose verified email (the `identity` user, [ADR-009](ADR-009-identity-and-account-model.md) point 4) is in `PLATFORM_OPERATOR_EMAILS`, a comma-separated list compared lower-case. In Azure it comes from the Key Vault secret `platform-operator-emails` through a secret reference in `infra/modules/web.bicep`; locally from `.env.local`. It is never in code, the database, the repository, issues or logs. Two operators for now; the code has no fixed count. Tests use the synthetic Pia Platform and Theo Platform ([personas](../00-product/personas.md)).
2. **Fail closed.** Unset, empty or invalid (any entry that is not an email) means nobody is an operator. An invalid list logs `platform operator config invalid` without its value. The app still starts and the recruiter app keeps working.
3. **Not a workspace role.** Being an operator gives no membership, no recruiter page, no "sign in as" and no impersonation. An operator who is also a member uses the recruiter app as that member. An operator who belongs to no workspace and opens the recruiter app (`/app`, where sign-in lands) is sent to `/ops` instead of the create-workspace page (amended by AIV-P2-058, 21 Nov 2026); that is the only path from the recruiter app into the console.
4. **A separate area.** The console is `/ops` in `apps/web` (route group `(ops)`, its own layout, `noindex`), not linked from the recruiter app or the candidate site. Operators sign in on the normal sign-in page, with the same External ID tenant and recruiter app registration. There is no second identity system.
5. **One policy on every entry point.** `platformOperator()` (`apps/web/src/server/operator.ts`) is awaited by every exported function of every `/ops` page, layout, template, route handler and server action. The architecture test `ops-platform-operator-policy` fails the build otherwise, within limits: it sees `export [default] [async] function` (not `export const x = async () =>`), and it finds the call textually, not as the first statement. Review catches the rest. A request with no session goes to `/sign-in?next=/ops`; anyone else gets 403. It reads the list and the user's email on every request (memoised within one request only). Nothing is cached in the session, so a removed email stops working on the next request after the app reloads its configuration (in Azure, a new revision).
6. **The metadata read path never bypasses RLS and needs no new role** (built in AIV-P2-036):
   - The console reads only platform metadata: workspace name, type, created date, synthetic flag, status, plan, member count, job count and AI token use. One exception, for the approvals page (AIV-P2-039): the email of a waiting workspace's creator, a recruiter and never a candidate, read from the identity user by the creator's opaque id so the operator can contact them. It is shown in the page body only, never in a URL or a log.
   - Each figure comes from a named, read-only contract method of the module that owns it (for example a workspace summary from `workspaces`, a job count from `jobs`). The method runs inside `withWorkspace(<that workspace>)` as `aivera_app`, under the unchanged tenant policies, and returns only those fields, as aggregates and opaque ids.
   - A job count runs with the job scope (`app.job_scope`, ADR-005 point 6) set to `all` for its own transaction, because the operator is not a member with grants. That is safe only because nothing but the number leaves the transaction; a read that returns rows never widens the scope this way.
   - To list workspaces, `workspaces` gets a platform-level table `workspaces.directory`: the workspace id and created date, nothing else. Like `workspaces.active_workspace`, it holds opaque ids only, so it has no tenant policy. `createWorkspace` writes it in the same transaction. AIV-P2-036 adds it with a Drizzle Kit migration and backfills dev from `active_workspace` (each creator gets a row there when they create a workspace). Built: the backfill reads each of those workspaces under its own `app.workspace_id`, so it misses a workspace that was nobody's active workspace (dev only, synthetic). The pilot database starts empty, so its directory is complete from the first workspace.
   - shortcut: one transaction per workspace on the list page. That is fine up to a few hundred workspaces. When it is slow, or the owner wants database-level column limits, switch to a dedicated `NOLOGIN` role `aivera_ops` with column grants and its own named policies. That needs the owner's bootstrap step, as `aivera_public` did.
   - What keeps it to metadata: the contracts return only the listed fields, and an architecture test added with the read path limits console code (`app/(ops)`, `features/ops*`, `server/ops*`, `modules/ops`) to an allow-list of contracts and never the raw pool. This is weaker than a database privilege, because a bug inside an owning module's method could read more. That trade-off buys no new role; `aivera_ops` is the upgrade.
   - Records that are not workspace-owned follow the same rule: subscriptions (AIV-P5-017) and erasure progress (AIV-P5-018) are read as aggregates and opaque ids, from records that hold no personal data, or per tenant inside that tenant's own scope. Never through a bypass.
7. **What operators can never see:** candidate names, contact details, CVs, documents, evidence, scores, rankings, interview notes, decisions and rubric content. Changes to one workspace, such as suspend (AIV-P2-037) or approve (AIV-P2-039), go through the owning module's contract inside `withWorkspace(<that workspace>)` as the normal app role.
8. **Audit.**
   - Every operator action goes to the platform audit log `audit.platform_entry`, which has no workspace id. It records the operator's user id, the action, the target's opaque id, the reason and the time. `aivera_app` may only insert: it has no `SELECT`, `UPDATE`, `DELETE` or `TRUNCATE`. The append-only triggers of `audit.entry` hold for every role. The console reads the log through one named read path (AIV-P2-053): the `SECURITY DEFINER` function `audit.list_platform_entries`, owned by the migrator with `search_path` pinned, which returns only the platform columns (id, time, operator user id, action, target opaque id, reason, `before`, `after`) newest first, filtered by action, operator, target and time range, with keyset pagination and at most 50 rows a call. `aivera_app` has `EXECUTE` on it and still no privilege on the table; `PUBLIC` (so `aivera_public`) cannot execute it. The `audit` contract method `listPlatformEntries` validates its input with zod before calling it, and the architecture rule `platform-audit-read-console-only` refuses a call outside console code (`app/(ops)`, `features/ops*`, `server/ops*`, `server/operator.ts`, `modules/ops`). `recordPlatform` refuses any `before` or `after` key outside the platform values (`PLATFORM_VALUE_KEYS`: AI budget, workspace status, approval mode), so no candidate field reaches the log. The function is created by a migration in the normal deploy: no owner database step.
   - An action on a workspace is also written to that workspace's `audit.entry`, in the same `withWorkspace(<that workspace>)` transaction as the change, with actor `operator:<user id>`. The first ticket that changes a workspace adds the `operator` actor type: built in AIV-P2-038 (the AI budget), which also gives `audit.platform_entry` `before` and `after` values and lets `recordPlatform` take the change's transaction, so both entries commit or roll back with the change. AIV-P2-037 (suspend) lists a workspace's operator actions on its detail page from the workspace's own log through the named read `audit.listOperatorEntries`, inside its scope, so `aivera_app` still has no `SELECT` on `audit.platform_entry`. A request context holds the workspace row under `FOR KEY SHARE` and a status change locks it `FOR UPDATE`, so a suspension waits for work in flight. AIV-P2-039 creates `modules/ops` for the platform settings (point 9) and adds the `pending_approval` and `rejected` statuses through the same request-context check.
   - Opening a workspace's detail page is recorded on the server, before the page renders (AIV-P2-036).
   - `ops.console_opened` is written once per browser session. A session cookie holding the operator's opaque id dedupes it, and sign-out clears the cookie. shortcut: the page calls the server action after it loads, so a client that blocks the call opens the landing page unrecorded; all reads of workspace data and all actions are recorded on the server.
9. **Where the code lives.** The platform audit log is in `audit`. `modules/ops` (`@credalent/ops`, schema `ops`) is created by the first ticket that stores something of its own: platform settings (AIV-P2-039) or role requests (AIV-P5-016). It reaches other modules only through their contracts, and no ranking module may import it (AGENTS.md 1.8).
10. **Open for the owner: a second factor for operators.** Recommendation: an External ID Conditional Access policy that requires MFA for an "Credalent operators" group. Use email one-time codes now, and an authenticator app once the tenant offers it. Then the app refuses `/ops` unless the ID token's `amr` claim shows a second factor (a follow-up ticket). Until the owner decides, operators sign in with the same password or Google sign-in as recruiters.

## Consequences

- No database role and no owner database step. The table migration runs in the normal deploy.
- On Azure dev, nobody can open the console until the owner creates the secret and applies the web Bicep change ([runbook](../runbooks/operator-console.md)). Until then it fails closed.
- Tenant policies, `FORCE ROW LEVEL SECURITY` and role attributes are unchanged. The tenancy suite (`tests/integration/src/tenancy.test.ts`) keeps proving it: every table with a `workspace_id` has RLS enabled, forced and the tenant policy, no Credalent role has `BYPASSRLS`, and `audit.platform_entry` is listed as a platform table with its reason.
- The metadata-only guarantee rests on contracts and an architecture test, not on database privileges, until `aivera_ops` exists.
