# ADR-006: AI on Azure AI Foundry, with citations, structured output and a person deciding

- **Status:** Accepted, 18 Nov 2026
- **Ticket:** AIV-P0-001
- **Amended by:** [ADR-013](ADR-013-catalogue-in-the-database.md) (proposed): a worker job may run the live eval for a catalogue draft (point 8); [ADR-015](ADR-015-python-ai-service.md): a Python AI service (accepted, built in AIV-P2-068) may do prompting and orchestration behind `@credalent/ai`, which keeps redaction, the token budget and the citation check (point 2)

## Context

Credalent uses language models to draft rubrics, read evidence, score competencies, write evidence requests, generate interview questions, tailor CVs and answer questions in the assistant. Hiring is a high-risk use of AI: a score must be explainable, a claim must never be passed off as evidence, and a model must never make the decision.

## Decision

1. **Provider.** Azure AI Foundry deployments (Azure OpenAI models) in UAE North, called through the AI SDK with `@ai-sdk/azure`, authenticated with managed identity. Embeddings: `text-embedding-3-large` into pgvector. CV and PDF text: Azure AI Document Intelligence. Before adopting a model, confirm it is deployable in UAE North; a model outside the region needs a new ADR. Dev's exception (Global Standard for `gpt-main`, synthetic data only) is [ADR-011](ADR-011-dev-ai-in-uae-north-global.md).
2. **One AI package** (`packages/ai`, `@credalent/ai`; a package rather than a module because it owns no tables, amended in AIV-P0-027) owns the client, prompt templates (versioned in code with an id like `assess-competency@3`), schemas and the eval harness. Other modules call its contracts; nothing else imports the AI SDK. **Amended in AIV-P0-033:** the per-workspace daily token budget is persisted, and the package still owns no tables. The client takes a narrow `TokenBudgetStore` port (`spentToday(workspaceId, day)`, `add(workspaceId, day, tokens)`), and the apps' composition root passes `createAiTokenBudget(db)` from `@credalent/workspaces/composition`. The `workspaces` module owns the table, `workspaces.ai_token_usage`: a workspace setting sits next to the workspace, and a new module would add a schema, contracts and composition for one table. The client fails closed (`AiUnavailable`, no model request) when the store cannot be read or written. `memoryTokenBudget()` is for unit tests only. No other module reads the table; the per-workspace budget override (AIV-P2-038) goes in the same module behind the same contract. **Amended in AIV-P2-038:** `spentToday` returns `{ spent, limit }` from one read, where `limit` is the operator's override (`workspaces.workspace.ai_daily_token_budget`, 100,000 to 10,000,000, a check constraint) or the platform default of 2,000,000 tokens per UTC day. The default and the bounds live in `workspaces` (`AI_DAILY_TOKEN_BUDGET`), so the client holds no budget figure of its own; `memoryTokenBudget(limit)` defaults to the same 2,000,000 for unit tests. A budget lowered below today's use stops the next call; calls in flight finish. **Amended in AIV-P0-030:** the package owns one table after all, `search.chunk` (workspace-scoped embeddings in pgvector: hashes, offsets and vectors, never the text), with its Drizzle schema and migrations in `packages/ai/src/infrastructure/` and its line in `packages/db/src/modules.ts`; `@credalent/ai/search` (`createSearchIndex`) is the only code that reads or writes it. Vectors are `halfvec(3072)`, the model's full size, because pgvector's HNSW index takes `vector` up to 2,000 dimensions only and `halfvec` up to 4,000.
3. **Structured output only** for anything that feeds the product: a zod schema per task, validated; output that fails validation is rejected and retried once, then surfaced as "could not assess", never patched.
4. **Citations are mandatory.** Every competency judgement returns the evidence ids and exact quoted spans it rests on, plus its limit. The application checks each cited id exists and each quoted span occurs in that evidence; an uncited judgement counts as a claim (zero in the backed score). **Amended in AIV-P0-028:** the client enforces this in `generateStructured({ task, workspaceId, promptVersion, system, prompt, schema, sources })`, the only generation call (no free-text call). The model sees the sources as `S1`, `S2`, ... and never their evidence ids; a statement built with `cited()` must cite at least one with a quote found verbatim (whitespace collapsed) in that source. Output that fails the schema, cites nothing, cites an unknown source or quotes text that is not there is rejected, never patched, and asked for once more; then the call throws `SchemaMismatch`, `UncitedOutput` or `InvalidCitation`, whose messages carry no model output. Schemas use `.nullable()` or a union, never `.optional()`: Azure checks them in strict mode, which needs every property. Each checked citation returns the evidence id and start and end offsets for `EvidenceHighlight`, and code sets `claim` on every statement whose only sources are the candidate's CV, whatever the model said. The task's template id and version (`jobs.draftCompetencies@1`) and the citation rules' version go on telemetry as `credalent.ai.template_version`.
5. **Evidence, not text, decides strength.** Provenance (corroborated, submitted, claim, contradictory, awaiting defence) comes from where the evidence came from and whether a second source confirms it, set by code, not by the model.
6. **A person decides.** Model output is a recommendation or a draft. Stage changes, messages, shares and decisions are previews that a person confirms (AGENTS.md 1.5). No model output ever rejects a candidate.
7. **Fairness inputs.** Prompts receive the evidence and the rubric, not the candidate's name, photo, age, nationality, gender or contact details. Those are stripped before the call. **Amended in AIV-P1-080:** the client replaces them once, in `@credalent/ai` (`packages/ai/src/identifiers.ts`), for every task. `generateStructured` takes the candidate's identifiers (`identifiers: { names, emails, phones }`, which the evidence module reads from the candidate record) and replaces them inside every source's text before the prompt is built; prompt modules and callers do not redact. A call that sends any source other than a job description without identifiers throws `MissingIdentifiers` before any model request or budget charge, so a new candidate-source task cannot skip the replacer. Names: the display name and each name part of two or more letters (split on spaces and hyphens), with possessives ("Sara's", "Al Qahtani's"), case-insensitive on word boundaries, become `[CANDIDATE]` (a run of parts is one placeholder); a particle (al, bin, abu, de, van, ...) is replaced only inside a run, so "Al Ain" stays a place. Emails: the record's and any other email-shaped string become `[EMAIL_1]`, `[EMAIL_2]`, ... (a referee's address is contact data too). Phones: the record's in any common formatting, and any other run of 8 to 15 digits separated by spaces, dashes or brackets that starts with `+`, `0` or a bracket or holds four digits in a row, or a dotted dialled or local number (`+971.50.123.4567`, `050.123.4567`), become `[PHONE_1]`, ...; decimals, dotted dates, year runs, ISO dates and metric lists are not phones. The same value gets the same placeholder within one call; the pairs exist only inside the call and are never stored, logged or returned. The model quotes the placeholder text and the citation contract checks each quote against it; the client maps each citation's offsets back and returns the stored text's span, so `EvidenceHighlight` marks the original. **Amended in AIV-P2-080:** a quote never brings an identifier back: when it spans a `[CANDIDATE]`, `[EMAIL_n]` or `[PHONE_n]` placeholder, the client keeps only its longest stretch between placeholders (spacing and separators trimmed off its ends) and returns that span of the stored text, so the highlight still marks the original and no stored quote holds the candidate's name, email or phone; a quote that is nothing but placeholders is rejected (`InvalidCitation`). Model text that keeps `[CANDIDATE]` is shown to a recruiter with the name put back by the evidence module after validation, never in the model's input. **The CV-parse exception:** only `evidence.parseCv` (`CONTACT_EXTRACTION_TASKS`, by task id) may send the CV's emails and phone numbers as written, because extracting the candidate's own contact onto the candidate record is its job; the name is still replaced. Every other task, including any later CV task, has emails and phones replaced. Its `contact` output goes to the candidate record only, never into a statement, claim, excerpt or later prompt: the evidence module drops a statement whose text repeats one of the extracted emails or phones (`cvClaims`), and every stored CV claim is a slice of the CV at its citation's offsets. Other people's names (referees, colleagues) are kept, only their emails and phones are replaced. **Amended in AIV-P2-065:** the same replacer also removes protected traits from CV, document and reference sources, whatever the task (the CV-parse exception covers emails and phones only; repository code such as `age: number;` is left alone). A labelled field (nationality, citizenship, date of birth, place of birth, age, marital, civil or family status, gender, sex, religion, photo), with its label in English or Arabic at a field start followed by a colon, a spaced dash or a tab, and its value up to the line end, the next `·`, `•`, `|` or `;`, or a comma before another `Label:` (or, after a bare label other than photo, the next line's first field when it is at most 40 characters with no colon), becomes `[REMOVED]`; so do "34 years old", "34-year-old", "aged 34", "Photo attached" and a bracketed photo reference. In a CV, two to four Arabic-script words become `[CANDIDATE]` when they are a field of the first line, the value of a `Name:` or `الاسم:` label (on its line or the next), or a whole line next to a line where the record's name matched (the first-line field and the matched name within 300 characters of their line start, which keeps the check linear on long lines); an Arabic-script name the record holds is replaced anywhere. A citation whose quote touches `[REMOVED]` is rejected (`InvalidCitation`), so a trait never comes back as a stored quote; `[REMOVED]` the model repeats in its own text is shown as written. An unlabelled trait in prose and an Arabic-script name the record does not hold, away from those places, are not detected. `pnpm ai:eval` fails a case whose `expected.prompt.forbidden` phrases are left in its sources as the model reads them (the `prompt` hard gate). **Amended in AIV-P2-081:** emails (`local@domain.tld`, the local part may hold any letter) are found first and masked, and names, phones and traits are matched only outside them, so a name run never eats an address and no name inside one is matched apart from it. A run of name parts may cross a line break or a no-break space. Under the CV-parse exception, the candidate's own email therefore goes as written, name parts included, and parseCv can extract it; for every other task it becomes `[EMAIL_n]`. A name part next to an `@` that is not a real email is still replaced.
8. **Eval set.** A golden set of synthetic candidates with expected scores and citations lives in `packages/ai/evals`. Every prompt or model change runs it in CI; a drop beyond the agreed tolerance fails the build. **Amended in AIV-P0-029:** each golden case (`packages/ai/evals/<task>/<case>.yaml`) holds its synthetic sources, the expected result and a recorded model answer. `pnpm ai:eval` scores the recorded answers by default, so the `ai-eval` workflow (on every pull request since AIV-P1-093, so it can be a required check, and on pushes to `main` that change `packages/ai` (which holds every prompt), `infra/modules/ai.bicep` or the workflow file) is deterministic and costs nothing; `--live` runs each task's registered prompt against the dev deployment within a token cap, in the separate `ai-eval-live` job (on `main` and manual runs only, never a pull request) under its own identity that may only call the dev AI resource. Citation validity, the citation contract (`checkOutput` from AIV-P0-028), claim labelling and safety cases must be 100% for every task; field match and the LLM judge have per-task thresholds in `evals/config.ts`. **Amended in AIV-P1-066:** a case may name a `group`, and a task may require a minimum share of a group's cases to pass every metric (`jobs.detectDomain`: domain accuracy 90%, no clear domain 5 of 6, fairness 100%); a group adds a gate and never relaxes a hard one. **Amended in AIV-P1-085:** each case of a task with a registered prompt stores, under `recorded`, the `promptVersion` it was recorded with and a `promptHash` of the request the client hands the model for that case: the deployment, the messages (system text with the shared citation and untrusted-content rules, the prompt, and the sources as the model reads them), the output schema, the temperature and the token limit. It is captured from the real client with a stub model, so no model is called. A recorded run fails a case whose version or hash differs from the code's (`recorded with <old>, code is <new>: re-record`), so a prompt edit cannot pass on answers the new prompt never produced, with or without a version bump; editing a case's input or sources fails it too. To re-record: ask the dev deployment with the new prompt (the live run scores answers and does not print them; a record command is AIV-P1-110), replace each stale case's `recorded.output` (and `recorded.judge`) with the answer the new prompt gave, and set `promptVersion` and `promptHash` to the values the failure line names. Changing the two stamps without a new answer defeats the gate: a reviewer rejects a diff that moves a stamp and leaves `recorded.output` as it was. The one exception is a hash that moves with no change to any prompt, schema, setting, case or source, because a dependency upgrade serialises the same request differently: the PR says so, shows the request is unchanged, and the owner approves the re-stamp. **Amended in AIV-P2-083:** a task may declare free-text paths (`meaning` in `packages/ai/evals/config.ts`: draft competency names, CV statement text) whose missed values match by meaning. Live, the matcher (`evals.match@1`) answers once per case for the values the output missed word for word, choosing only among output values that no expected value already matches exactly, each at most once. Its verdicts are written per case in the `--out` results, and a re-recording stores them as `recorded.matches` beside `recorded.output`, so the recorded run scores them with no model call. Every other path stays exact. **Amended in AIV-P1-140:** on a `meaning` path, a missed value that equals a free output value once case, surrounding space and trailing punctuation (`.,;:!?`) are set aside matches in code, with no matcher call (gpt-4.1 answered null for a CV statement copied word for word with a period added). Code matches settle first and reserve their output value, so the matcher is offered only values still unused; and a verdict names the free output value it equals after the same normalisation, so a verdict that drops its option's period still names that option. The matcher prompt is unchanged (`evals.match@1`). Ids, enums, emails and phones stay exact, punctuation and case included. **Amended in AIV-P2-084:** the LLM judge has its own golden cases (`packages/ai/evals/judge/<case>.yaml`): a golden case's output, as recorded or with every limit replaced, and the verdict the judge must give it (the good answer passes; praise, a limit naming nothing and a limit the sources contradict fail). They run as `evals.judge`: live, the judge grades them on the real model; recorded, their stored verdicts are replayed, and a verdict stored with another judge prompt id than the code's fails (`re-run the judge golden cases live`). Every case must get its expected verdict. A judge prompt change records each case's live pass rate over 3 runs on its PR. **Amended in AIV-P2-085:** a drafted suggestion is scored by what it is, not by whether it is the golden pair. The golden case's suggestion names still set how many suggestion points it has; each point passes with an output suggestion that cites a line and that the suggestion judge (`evals.suggestion@2`, one call per case, one yes/no answer per rule, the fault chosen in code) finds implied by the work described, not a listed competency again, not a proxy and not a generic soft skill, with a cited line that implies it. Each bad suggestion, or a repeated name, costs a point, and a proxy also fails the safety hard gate. Its verdicts are stored as `recorded.suggestions` with the judge's prompt id, and a recorded run refuses verdicts from another judge prompt. Bad-suggestion cases (a generic soft skill, a listed competency reworded, a proxy, no citation) in `evals/fixtures/failing` and the golden pair and a plausible suggestion that is not the golden pair in `evals/fixtures/passing` pin the judge; they are hand-made answers by design, stamped with the prompt in code so they are scored, and their verdicts come from the live judge. shortcut: the judge may miss a subtle rewording of a listed competency (on `gpt-main`, a tool-named version of a listed skill could pass); add per-case acceptable answers when the live eval shows one reaching a draft. **Amended in AIV-P1-075:** the judge, the matcher and the suggestion judge (task `evals.judge`) run on their own deployment `gpt-judge`, a stronger model than the tasks they grade on dev (gpt-4.1, [ADR-011](ADR-011-dev-ai-in-uae-north-global.md)); the pilot's is gpt-4.1-mini, the same model as its tasks, until gpt-4.1 is on regional Standard in UAE North. On `gpt-main` the live judge passed a limit its sources contradict, and so did gpt-4.1 with a bare verdict: from `evals.judge@5` the judge first writes one check per item the rubric speaks of (the item, what its cited source says, whether it meets the rubric), and code fails an output when any check fails, whatever the verdict. Live on 25 Nov 2026, the four judge golden cases got their expected verdicts in 3 of 3 runs. Recorded verdicts are stamped by prompt id only, so after a judge model change every judge golden case and suggestion fixture is re-run live, 3 runs each. **Amended in AIV-P2-082:** the live `jobs.detectDomain` eval scores the answer after the guard the jobs module applies (`regionsNotAboutPeople`, `@credalent/ai`): a region whose only citation is a line about the people to hire is dropped before scoring. The raw gpt-4.1-mini answer still cites a nationality line for a region; the eval no longer sees that while the guard's keyword list matches it (a `shortcut:` in `evals/config.ts`). **Amended in AIV-P2-088:** the suggestion judge is graded by the same judge golden cases, so its six fixtures are re-graded on the real model on every live run. A case in `evals/judge` with `judge: suggestion` names a fixture (`from: failing` or `passing`, `case: jobs.draftCompetencies/<id>`) and, for every suggestion in it in order, the fault the judge must give it or null. `loadJudgeCases` loads both kinds and `evaluateJudge` grades both as `evals.judge`: live, the suggestion judge grades the fixture's output on `gpt-judge`; recorded, the fixture's own `recorded.suggestions` are replayed, so verdicts are stored once, and verdicts stamped with another suggestion judge prompt than the code's fail (`re-run the judge golden cases live`). A miss names the case, the suggestion's position and the expected and given fault, never the suggestion's name. On gpt-4.1 the judge gave no verdict at all for a suggestion that cites nothing (`suggestion-no-citation`, 3 of 3 runs), so the `citation` fault for a suggestion with no citations is decided in code (`liveSuggestionJudge`), as `faultOf` decides the others: it is a fact code sees, not a judgement, and a graver fault the judge gives (a proxy) stays. With that, live on 25 Nov 2026 (gpt-4.1, 3 runs), all ten judge golden cases (four evidence, six suggestion) got their expected verdicts in 3 of 3 runs. **Amended in AIV-P1-142:** on gpt-4.1, `evals.match@1` answered null for a drafted competency that names the expected skill as the job's own activity, skipped every expected text of a case (an empty list) on some runs of the same request at temperature 0, and gave one option to two expected texts, so `jobs.draftCompetencies` passed or failed its 90% field match by chance (85.8–89.7% on 3 live runs). From `evals.match@2` the matcher is asked per option, not per expected text: every option offered is a required key whose answer is the expected text it means or null, and code gives an option to that miss only if the miss offered it and has no match yet, so no option counts twice and none goes unanswered. A competency name means the same when the option is that skill worded as an activity, narrowed to the job or named with a second skill, and not when it is a related but different skill; a CV statement still means the same only when it states the same fact. The matcher has its own judge golden cases (`judge: match`: options, the option or null each expected text must get, and the live verdicts stamped with the matcher prompt; a recorded run refuses another prompt's), so every live run re-grades it. Live on 26 Nov 2026: `jobs.draftCompetencies` field match 97.4% on 3 of 3 runs, and the three matcher cases got their expected verdicts in 3 of 3 runs. **Amended in AIV-P1-144:** on 26 Nov 2026 `evals.judge@5` passed the false limit of `contradicted-limit` in about 3 of 50 live runs, so `ai-eval-live` on `main` could go red by chance. In each wrong run the check for the c-python link quoted S1's authored commit count and still marked the limit as meeting the rubric. 9. **No candidate data in logs or telemetry**: log the prompt id, model, token counts, latency and outcome only.

## Consequences

- Scores are reproducible from stored evidence plus a prompt id and model version, which are saved with each assessment.
- Changing a model is a measured change, not a silent one.
- Some judgements will come back "could not assess"; the UI treats that as a gap, not a low score.
