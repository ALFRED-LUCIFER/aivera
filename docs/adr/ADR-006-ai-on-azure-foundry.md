# ADR-006: AI on Azure AI Foundry, with citations, structured output and a person deciding

- **Status:** Accepted, 18 Nov 2026
- **Ticket:** AIV-P0-001
- **Amended by:** [ADR-013](ADR-013-catalogue-in-the-database.md) (proposed): a worker job may run the live eval for a catalogue draft (point 8)

## Context

Credalent uses language models to draft rubrics, read evidence, score competencies, write evidence requests, generate interview questions, tailor CVs and answer questions in the assistant. Hiring is a high-risk use of AI: a score must be explainable, a claim must never be passed off as evidence, and a model must never make the decision.

## Decision

1. **Provider.** Azure AI Foundry deployments (Azure OpenAI models) in UAE North, called through the AI SDK with `@ai-sdk/azure`, authenticated with managed identity. Embeddings: `text-embedding-3-large` into pgvector. CV and PDF text: Azure AI Document Intelligence. Before adopting a model, confirm it is deployable in UAE North; a model outside the region needs a new ADR. Dev's exception (Global Standard for `gpt-main`, synthetic data only) is [ADR-011](ADR-011-dev-ai-in-uae-north-global.md).
2. **One AI package** (`packages/ai`, `@credalent/ai`; a package rather than a module because it owns no tables, amended in AIV-P0-027) owns the client, prompt templates (versioned in code with an id like `assess-competency@3`), schemas and the eval harness. Other modules call its contracts; nothing else imports the AI SDK. **Amended in AIV-P0-033:** the per-workspace daily token budget is persisted, and the package still owns no tables. The client takes a narrow `TokenBudgetStore` port (`spentToday(workspaceId, day)`, `add(workspaceId, day, tokens)`), and the apps' composition root passes `createAiTokenBudget(db)` from `@credalent/workspaces/composition`. The `workspaces` module owns the table, `workspaces.ai_token_usage`: a workspace setting sits next to the workspace, and a new module would add a schema, contracts and composition for one table. The client fails closed (`AiUnavailable`, no model request) when the store cannot be read or written. `memoryTokenBudget()` is for unit tests only. No other module reads the table; the per-workspace budget override (AIV-P2-038) goes in the same module behind the same contract. **Amended in AIV-P2-038:** `spentToday` returns `{ spent, limit }` from one read, where `limit` is the operator's override (`workspaces.workspace.ai_daily_token_budget`, 100,000 to 10,000,000, a check constraint) or the platform default of 2,000,000 tokens per UTC day. The default and the bounds live in `workspaces` (`AI_DAILY_TOKEN_BUDGET`), so the client holds no budget figure of its own; `memoryTokenBudget(limit)` defaults to the same 2,000,000 for unit tests. A budget lowered below today's use stops the next call; calls in flight finish. **Amended in AIV-P0-030:** the package owns one table after all, `search.chunk` (workspace-scoped embeddings in pgvector: hashes, offsets and vectors, never the text), with its Drizzle schema and migrations in `packages/ai/src/infrastructure/` and its line in `packages/db/src/modules.ts`; `@credalent/ai/search` (`createSearchIndex`) is the only code that reads or writes it. Vectors are `halfvec(3072)`, the model's full size, because pgvector's HNSW index takes `vector` up to 2,000 dimensions only and `halfvec` up to 4,000.
3. **Structured output only** for anything that feeds the product: a zod schema per task, validated; output that fails validation is rejected and retried once, then surfaced as "could not assess", never patched.
4. **Citations are mandatory.** Every competency judgement returns the evidence ids and exact quoted spans it rests on, plus its limit. The application checks each cited id exists and each quoted span occurs in that evidence; an uncited judgement counts as a claim (zero in the backed score). **Amended in AIV-P0-028:** the client enforces this in `generateStructured({ task, workspaceId, promptVersion, system, prompt, schema, sources })`, the only generation call (no free-text call). The model sees the sources as `S1`, `S2`, ... and never their evidence ids; a statement built with `cited()` must cite at least one with a quote found verbatim (whitespace collapsed) in that source. Output that fails the schema, cites nothing, cites an unknown source or quotes text that is not there is rejected, never patched, and asked for once more; then the call throws `SchemaMismatch`, `UncitedOutput` or `InvalidCitation`, whose messages carry no model output. Schemas use `.nullable()` or a union, never `.optional()`: Azure checks them in strict mode, which needs every property. Each checked citation returns the evidence id and start and end offsets for `EvidenceHighlight`, and code sets `claim` on every statement whose only sources are the candidate's CV, whatever the model said. The task's template id and version (`jobs.draftCompetencies@1`) and the citation rules' version go on telemetry as `credalent.ai.template_version`.
5. **Evidence, not text, decides strength.** Provenance (corroborated, submitted, claim, contradictory, awaiting defence) comes from where the evidence came from and whether a second source confirms it, set by code, not by the model.
6. **A person decides.** Model output is a recommendation or a draft. Stage changes, messages, shares and decisions are previews that a person confirms (AGENTS.md 1.5). No model output ever rejects a candidate.
7. **Fairness inputs.** Prompts receive the evidence and the rubric, not the candidate's name, photo, age, nationality, gender or contact details. Those are stripped before the call. **Amended in AIV-P1-080:** the client replaces them once, in `@credalent/ai` (`packages/ai/src/identifiers.ts`), for every task. `generateStructured` takes the candidate's identifiers (`identifiers: { names, emails, phones }`, which the evidence module reads from the candidate record) and replaces them inside every source's text before the prompt is built; prompt modules and callers do not redact. A call that sends any source other than a job description without identifiers throws `MissingIdentifiers` before any model request or budget charge, so a new candidate-source task cannot skip the replacer. Names: the display name and each name part of two or more letters (split on spaces and hyphens), with possessives ("Sara's", "Al Qahtani's"), case-insensitive on word boundaries, become `[CANDIDATE]` (a run of parts is one placeholder); a particle (al, bin, abu, de, van, ...) is replaced only inside a run, so "Al Ain" stays a place. Emails: the record's and any other email-shaped string become `[EMAIL_1]`, `[EMAIL_2]`, ... (a referee's address is contact data too). Phones: the record's in any common formatting, and any other run of 8 to 15 digits separated by spaces, dashes or brackets that starts with `+`, `0` or a bracket or holds four digits in a row, or a dotted dialled or local number (`+971.50.123.4567`, `050.123.4567`), become `[PHONE_1]`, ...; decimals, dotted dates, year runs, ISO dates and metric lists are not phones. The same value gets the same placeholder within one call; the pairs exist only inside the call and are never stored, logged or returned. The model quotes the placeholder text and the citation contract checks each quote against it; the client maps each citation's offsets back and returns the stored text's span, so `EvidenceHighlight` marks the original. Model text that keeps `[CANDIDATE]` is shown to a recruiter with the name put back by the evidence module after validation, never in the model's input. **The CV-parse exception:** only `evidence.parseCv` (`CONTACT_EXTRACTION_TASKS`, by task id) may send the CV's emails and phone numbers as written, because extracting the candidate's own contact onto the candidate record is its job; the name is still replaced. Every other task, including any later CV task, has emails and phones replaced. Its `contact` output goes to the candidate record only, never into a statement, claim, excerpt or later prompt: the evidence module drops a statement whose text repeats one of the extracted emails or phones (`cvClaims`), and every stored CV claim is a slice of the CV at its citation's offsets. Other people's names (referees, colleagues) are kept, only their emails and phones are replaced. **Amended in AIV-P2-065:** the same replacer also removes protected traits from CV, document and reference sources, whatever the task (the CV-parse exception covers emails and phones only; repository code such as `age: number;` is left alone). A labelled field (nationality, citizenship, date of birth, place of birth, age, marital, civil or family status, gender, sex, religion, photo), with its label in English or Arabic at a field start followed by a colon, a spaced dash or a tab, and its value up to the line end, the next `·`, `•`, `|` or `;`, or a comma before another `Label:`, becomes `[REMOVED]`; so do "34 years old", "34-year-old", "aged 34", "Photo attached" and a bracketed photo reference. In a CV, two to four Arabic-script words become `[CANDIDATE]` when they are a field of the first line, the value of a `Name:` or `الاسم:` label, or a whole line next to a line where the record's name matched; an Arabic-script name the record holds is replaced anywhere. A citation whose quote touches `[REMOVED]` is rejected (`InvalidCitation`), so a trait never comes back as a stored quote; `[REMOVED]` the model repeats in its own text is shown as written. An unlabelled trait in prose and an Arabic-script name the record does not hold, away from those places, are not detected. `pnpm ai:eval` fails a case whose `expected.prompt.forbidden` phrases are left in its sources as the model reads them (the `prompt` hard gate).
8. **Eval set.** A golden set of synthetic candidates with expected scores and citations lives in `packages/ai/evals`. Every prompt or model change runs it in CI; a drop beyond the agreed tolerance fails the build. **Amended in AIV-P0-029:** each golden case (`packages/ai/evals/<task>/<case>.yaml`) holds its synthetic sources, the expected result and a recorded model answer. `pnpm ai:eval` scores the recorded answers by default, so the `ai-eval` workflow (on every pull request since AIV-P1-093, so it can be a required check, and on pushes to `main` that change `packages/ai` (which holds every prompt), `infra/modules/ai.bicep` or the workflow file) is deterministic and costs nothing; `--live` runs each task's registered prompt against the dev deployment within a token cap, in the separate `ai-eval-live` job (on `main` and manual runs only, never a pull request) under its own identity that may only call the dev AI resource. Citation validity, the citation contract (`checkOutput` from AIV-P0-028), claim labelling and safety cases must be 100% for every task; field match and the LLM judge have per-task thresholds in `evals/config.ts`. **Amended in AIV-P1-066:** a case may name a `group`, and a task may require a minimum share of a group's cases to pass every metric (`jobs.detectDomain`: domain accuracy 90%, no clear domain 5 of 6, fairness 100%); a group adds a gate and never relaxes a hard one.
9. **No candidate data in logs or telemetry**: log the prompt id, model, token counts, latency and outcome only.

## Consequences

- Scores are reproducible from stored evidence plus a prompt id and model version, which are saved with each assessment.
- Changing a model is a measured change, not a silent one.
- Some judgements will come back "could not assess"; the UI treats that as a gap, not a low score.
