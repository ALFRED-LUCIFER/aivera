# Modules

The back end is a modular monolith ([ADR-002](../adr/ADR-002-repository-layout.md)). Each module is a package `modules/<m>` (`@aivera/<m>`) that owns one PostgreSQL schema of the same name ([ADR-004](../adr/ADR-004-database-and-migrations.md)). Other code imports only its contracts. This map is the plan; a module is created by the ticket that builds it, which updates its row.

## Rules that the architecture test enforces

- A module imports another module only as `@aivera/<m>` (its contracts).
- `assessment`, `jobs` and `intake` never import `billing` or `portfolio` (AGENTS.md 1.8: paying never changes ranking).
- No recruiter-side module imports `candidate-accounts`, so nothing on the recruiter side can tell that a recruiter is also a candidate ([ADR-009](../adr/ADR-009-identity-and-account-model.md); rule added with the module in AIV-P3-006).
- No module imports an app, `packages/ui` or `packages/tokens`.

## Identity, clients and job scope ([ADR-009](../adr/ADR-009-identity-and-account-model.md))

- **Clients live in `workspaces`, not in their own module.** A client is a name that groups jobs and grants inside one workspace, with no behaviour of its own. A separate module would add a schema, contracts and composition for one table. `jobs.job` holds the client as an opaque `client_id`.
- **Job grants live in `workspaces`** next to the member and role they qualify, so the request context loads role and grants in one place (ADR-005, point 6).
- **The candidate-account link lives in `candidate-accounts`.** The account belongs to the person; recruiter-side modules (`candidates`, `intake`, `evidence`) never store an account id. Erasure reaches each linked workspace as an event carrying opaque workspace and candidate ids.
- Only apps import `@aivera/<m>/composition`.

## Tracing across the outbox ([AIV-P0-018](https://github.com/ALFRED-LUCIFER/aivera/issues/50))

One operation id runs from the server action to the worker handler. The outbox envelope carries `correlationId`: the W3C `traceparent` of the span active when the event is written (`propagation.inject`). The relay and the worker start their spans with it as parent (`propagation.extract`). It holds trace and span ids only, never personal data. Built and tested by the outbox (AIV-P0-014, #46) and worker (AIV-P0-015, #47) tickets.
