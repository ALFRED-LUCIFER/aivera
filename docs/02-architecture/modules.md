# Modules

The back end is a modular monolith ([ADR-002](../adr/ADR-002-repository-layout.md)). Each module is a package `modules/<m>` (`@credalent/<m>`) that owns one PostgreSQL schema of the same name ([ADR-004](../adr/ADR-004-database-and-migrations.md)). Other code imports only its contracts. This map is the plan; a module is created by the ticket that builds it, which updates its row.

## Rules that the architecture test enforces

- A module imports another module only as `@credalent/<m>` (its contracts).
- `assessment`, `jobs`, `intake` and `interviews` never import `billing` or `portfolio` (AGENTS.md 1.8: paying never changes ranking).
- No recruiter-side module imports `candidate-accounts`, so nothing on the recruiter side can tell that a recruiter is also a candidate ([ADR-009](../adr/ADR-009-identity-and-account-model.md); rule added with the module in AIV-P3-006).
- No module imports an app, `packages/ui` or `packages/tokens`.

## Identity, clients and job scope ([ADR-009](../adr/ADR-009-identity-and-account-model.md))

- **Clients live in `workspaces`, not in their own module.** A client is a name that groups jobs and grants inside one workspace, with no behaviour of its own. A separate module would add a schema, contracts and composition for one table. `jobs.job` holds the client as an opaque `client_id`.
- **Job grants live in `workspaces`** next to the member and role they qualify, so the request context loads role and grants in one place (ADR-005, point 6).
- **The candidate-account link lives in `candidate-accounts`.** The account belongs to the person; recruiter-side modules (`candidates`, `intake`, `evidence`) never store an account id. Erasure reaches each linked workspace as an event carrying opaque workspace and candidate ids.
- Only apps import `@credalent/<m>/composition`.

## Tracing across the outbox ([AIV-P0-018](https://github.com/ALFRED-LUCIFER/aivera/issues/50))

One operation id runs from the server action to the worker handler. The outbox envelope carries `correlationId`: the W3C `traceparent` of the span active when the event is written (`propagation.inject`). The relay and the worker start their spans with it as parent (`propagation.extract`). It holds trace and span ids only, never personal data. Built and tested: the outbox half in `tests/integration/src/outbox.test.ts` (AIV-P0-014), the worker handler half in `tests/integration/src/worker.test.ts` (AIV-P0-015).

## Events through the outbox ([AIV-P0-014](https://github.com/ALFRED-LUCIFER/aivera/issues/46))

- **Publish.** The module defines its event in its contracts as `{ type: 'Name.v1', payload: z.strictObject({ …ids }) }` (`EventDefinition` from `@credalent/db`). Strict, so a field the schema does not name, such as an email, is refused. It calls `enqueue(tx, outbox, event, { workspaceId, payload, dedupeKey, occurredAt })` in the same transaction as the change, so a rollback leaves no event. The same `dedupeKey` in a workspace is written once.
- **Each module owns `<m>.outbox`.** Export `outboxTable(<m>)` from the module's `schema.ts`, generate the migration, and add the custom migration that `outboxTable` documents (FORCE row-level security and the grants below). See `modules/candidates` (migrations 0002 and 0003).
- **Envelope.** `{ id, type, workspaceId, occurredAt, payload, correlationId }` is the Service Bus message body, and `id` (UUIDv7) is its `messageId`.
- **Relay.** `createRelay` (`@credalent/db/relay`) runs in `apps/backend/worker`. Each pass claims due unsent rows with `FOR UPDATE SKIP LOCKED`, so two replicas never claim the same row. It sends each row, then marks it sent or retries it with back-off (1 s doubling to 5 minutes), all in the claiming transaction. It records the `credalent.outbox.lag` histogram (written to sent, ms). `apps/backend/worker/src/main.ts` maps each event type to the consuming module's queue (`infra/modules/messaging.bicep`). An event with no queue stays unsent and is retried.
- **Delivery is at least once.** A relay that crashes after a send and before its commit sends the event again with the same message id. Dev runs Service Bus Basic, which has no duplicate detection, so consumers deduplicate on the message id in their inbox (AIV-P0-015).
- **The relay's own role, `aivera_relay`.** The relay reads every workspace's events, so it cannot run as `aivera_app` under the tenant policy. A role that bypasses RLS is ruled out (ADR-005 point 4), and so is `SET ROLE` from the app role, which would let the web app do the same. Each outbox therefore carries two named policies for `aivera_relay` only: `outbox_relay_read` (SELECT) and `outbox_relay_mark` (UPDATE). The role is granted `SELECT` and `UPDATE (attempts, next_attempt_at, sent_at)` on outbox tables and nothing else: it cannot read a person or change a payload. `aivera_app` loses `UPDATE` and `DELETE` on the outbox, so app code cannot suppress an event. In Azure the role maps to its own managed identity, `id-aivera-relay-dev`.

## Consumers in the worker host ([AIV-P0-015](https://github.com/ALFRED-LUCIFER/aivera/issues/47))

- **Handlers.** A consuming module exports a `Handler` (`@credalent/db/consumer`) per event type from its infrastructure: `{ event, inbox, consumer, handle(tx, payload, envelope) }`. `apps/backend/worker/src/main.ts` lists each queue's handlers in `CONSUMERS`.
- **Each consuming module owns `<m>.inbox`.** Export `inboxTable(<m>)` from its `schema.ts`, generate the migration, and add a custom one with `FORCE ROW LEVEL SECURITY`. The wrapper inserts `(consumer, message id)` in the envelope's workspace transaction, before the handler; a duplicate delivery finds the row and is completed without work, and a failed handler rolls the row back with its work.
- **Settlement** (`decide`): handled → complete; envelope or payload failing its schema, or an unknown type → dead-letter at once (`invalid payload`, `unknown event type`); a thrown error → abandon after a back-off (1 s doubling, at most 30 s, under the 1-minute lock), dead-letter on the tenth delivery (`max deliveries`). Dead letters count in `credalent.worker.dead_lettered` per queue; the alert watches the Service Bus `DeadletteredMessages` metric, which also counts TTL expiry.
- **Scheduled messages.** `createScheduler` (`apps/backend/worker/src/serviceBus.ts`) gives the `Scheduler` port: `schedule(queue, envelope, at)` returns the sequence number, and `cancel(queue, sequenceNumber)` removes it. The caller stores the sequence number. Build the envelope with `newEnvelope(event, …)`. Not wired yet: scheduling needs a Service Bus send role for the consumers' identity, which AIV-P1-040 adds with the first follow-up.
- **Shutdown.** SIGTERM stops the relay loop and the receivers, lets each message in flight finish (one waiting out a back-off is abandoned at once), then closes. A message whose lock lapses is redelivered, never lost.
