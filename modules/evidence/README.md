# @credalent/evidence

Everything a score can rest on (AIV-P1-024): where a piece of evidence came from, the exact excerpt it cites, its provenance, its strength and what it does not show. Other code imports only `@credalent/evidence` (the `EvidenceContract` types); apps build it with `createEvidence(workspaces, audit, now)` from `@credalent/evidence/composition`.

- **Tables:** `evidence.source` (candidate id, kind `cv | repository | document | shipped_product | reference_call | portal_submission | interview_note`, label, https url or blob file id, `captured_at`, `checked_at` and `check_method` such as "Commit history", `synthetic`), `evidence.item` (source, candidate, excerpt, excerpt span such as "page 2", provenance, strength, `limit_statement`, `synthetic`), `evidence.competency_link` (item, job id, competency id of the jobs module, and the `level` 0–5 the item shows for that competency, 0 until mapped), `evidence.duplicate_flag` (AIV-P1-071) `evidence.repository_read`, `evidence.merged_pull_request`, `evidence.repository_skill_signal` and `evidence.repository_skill_grade` (below), `evidence.inbox` (handled message ids) and `evidence.outbox`. Candidate, job and competency ids are opaque: no foreign key across modules. The foreign key `(workspace_id, source_id, candidate_id)` keeps an item on its own workspace's and candidate's source. Migrations are tracked in `migrations.evidence`.
- **Provenance and strength** are closed lists, with the values `ProvenanceTag` and `StrengthMeter` of `@credalent/ui` take: provenance `corroborated | submitted | claim | contradictory | awaiting-defence`, strength `strong | medium | supporting | claim` (the Rubric page's scoring definitions). Labels: `evidence.provenance.*` and `rubric.strength.*` in `packages/i18n`.
- **Invariants:** a `claim` or `awaiting-defence` item is never stronger than Supporting ("A claim cannot be stronger than Supporting"), and every item states its limit ("State what this evidence does not show"). The domain (`checkItem`) refuses both before anything is written, and check constraints refuse them again for any write path. "Claim only" counting zero is scoring's rule (AIV-P1-030).
- **Contract:** `recordEvidence(ctx, { candidateId, source, items, synthetic })` stores a source, its items and their competency links; `linkToCompetency(ctx, itemId, { jobId, competencyId, level })` adds a link once, at the latest level ("A level is a whole number from 0 to 5"); `listEvidenceForCandidate(ctx, candidateId, jobId)` returns the candidate's items with their source and their links to that job (an empty list when there are none); each source carries `via`, how its repository read came about (`cv_profile`, or null), for the profile's source chip (AIV-P1-118), never the read's login or emails, and never read by assessment; `getEvidenceItem(ctx, id)`; `purgeSyntheticEvidence(ctx)` for the demo seed's reset.
- **Authorisation:** through the workspaces `authorize`: recording and linking as `candidate.create`, reading as `candidate.view` with no job, so admins and recruiters only until applications give a job to check (AIV-P1-017).
- **Row-level security (ADR-005):** every table `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`; the repository also filters by workspace.
- **Event:** `EvidenceRecorded.v1` (the ticket's "evidence.recorded"; `{ candidateId, sourceId, itemIds }`, strict, opaque ids only) is written to `evidence.outbox` in the transaction that records the evidence; the relay sends it to the `assessment` queue.
- **Personal data (AGENTS.md 1.2):** labels, urls, excerpts and limits are candidate personal data (`PERSONAL_DATA_FIELDS`). The module never logs; `EvidenceError` never repeats the refused value.
- **Fingerprints (AIV-P1-071):** `recordEvidence` takes an optional `text` (a write-up's or document's prose) and stores only its 64-bit SimHash as `source.text_fingerprint` (16 hex characters, check constraint), never the text. `domain/fingerprint.ts` (ported, MIT, see `THIRD_PARTY_NOTICES.md`) normalises the text, drops CV boilerplate (contact details, lines of up to three words, heading lines, short lists such as "Python, SQL, Docker"), and gives no fingerprint below `FINGERPRINT_MIN_TEXT` (200 normalised characters); no fingerprint never matches. Near-duplicate means similarity (1 − differing bits/64) at least `NEAR_DUPLICATE_THRESHOLD` (0.92).
- **Origins and flags:** `listOriginGroups(ctx, candidateId)` groups one candidate's near-duplicate sources into one origin (for AIV-P1-029). When another candidate's source in the same workspace is a near-duplicate, `recordEvidence` writes an `evidence.duplicate_flag` ("Also submitted by another applicant") citing both sources by id; `listDuplicateFlags(ctx, candidateId)` returns the flags on either side. A flag changes no score, rank, stage or contact. `resolveDuplicateFlag(ctx, flagId, reason)` (`shared_group_project | same_template | needs_follow_up`, labels `evidence.duplicate.*`) is admins and recruiters only (`candidate.create`) and audited as `evidence.flag_resolved`, last. Comparisons take a per-workspace advisory lock until commit, so two copies recorded at once still flag each other. The raised flag is logged with the flag and source ids and `credalent.evidence.similarity` only. Showing the flag on the candidate profile is the profile tickets' (AIV-P1-043 #107, AIV-P1-045 #109).
- **GitHub repositories (AIV-P1-026):** `requestRepositoryRead(ctx, { candidateId, url, githubLogin, emails, synthetic })` stores a pending `repository` source for a public `https://github.com/<owner>/<repo>` link, the login and emails in `evidence.repository_read`, and writes `RepositoryReadRequested.v1` (opaque ids) for the `evidence` queue. The worker job `evidence.repository.read` (`createRepositoryReadHandler`, a GitHub App installation token, every answer zod-checked) reads metadata, languages, last push, the file list (tests and CI presence; no contents) and the commit list. **Authorship rules** (`src/domain/repository.ts`): a commit is the candidate's only by login, a supplied email or a Co-authored-by trailer, never by owning the repository; a fork gets status `fork` and nothing is measured or scored; a 404 or private repository gets `not_accessible`; commits that only touch lockfiles, vendored or built paths are counted apart and left out of the share (`getRepositoryRead` gives the share, its class `clear | shared | minor` and the strength cap: Strong only when clear). The item reads "authored 412 of 460 commits, 38 only touch generated files" and is at most Medium (a second source is AIV-P1-029); the source is checked by "Commit history". Pull requests the candidate authored and merged into repositories they neither own nor forked are items of their own in `evidence.merged_pull_request` (repository, number, merged date, `merged_by`, `self_merged`), never added to the commit count. A spent rate limit schedules the request on Service Bus for after `x-ratelimit-reset`; the source stays pending. **One read per link (AIV-P1-076):** a link is stored as `https://github.com/<owner>/<repo>` lower case, without `.git`, trailing slash, query or fragment, and `repository_read_candidate_url_key` (workspace, candidate, URL) keeps one read per candidate and repository, concurrent requests included; a second request returns the first `sourceId` and writes no second event. The worker job `evidence.application.received` (`createApplicationReceivedHandler`, fed by the intake and candidates system reads from the worker) consumes `ApplicationReceived.v1` and queues a read for each GitHub repository link on the arrival or a member's link (`queueArrivalReads`); other links stay on the application. Identity is only what the candidate supplied: their login (an invalid one is dropped, never guessed) and their email identifiers, never CV contact on their record (AIV-P1-087). Identifier emails are what the applicant supplied, not proven to be theirs (`shortcut:` until email verification exists, then require proof of control); a read queued before AIV-P1-087 keeps the emails it was queued with. With no login (`github_login` null) commits match by email only, no merged pull requests are searched, the item's limit starts "Authorship unclear: no GitHub login supplied." and the cap is Medium. Logs carry the source and candidate ids only. CV parsing (AIV-P1-025) calls `queueRepositoryRead` for each repository URL it finds, except one inside text aimed at the AI or hidden in the file (AIV-P1-119). Caps (`shortcut:`): generated-only check on the newest 300 authored commits, commit list 5,000, first 100 merged pull requests. Statuses' copy: `evidence.repositoryStatus.*` in `packages/i18n`.
- **Evidence requests (AIV-P1-037):** `createDraftRequest(ctx, { candidateId, jobId })` makes a draft naming only the candidate's open claims for the job (one line per competency, from items resting on "Claim awaiting validation" or "To check in interview"; "Nothing rests on a claim for this job" when there are none), with the default follow-up policy (after 2 days, at most twice). One open request per candidate per job (partial unique index, mapped to "This candidate already has an open request for this job"). Status moves are compare-and-set, so racing moves cannot skip the table. Open claims come from the candidate's evidence items, not the assessment snapshot: evidence cannot depend on assessment (assessment reads evidence), so a claim on a competency outside the approved rubric, or one already proven by other work, still appears; the request screen (AIV-P1-038), which can read both, narrows it. State machine (`domain/request.ts`): draft → sent only by a person (`sendRequest`, which issues the portal token and returns it once; only its SHA-256 is stored, valid 30 days) → opened → answered | quiet, recorded by the system (`createRequestOutcomeRecorder` from the composition: a workspace-scoped transaction with no member, for the follow-up worker and the portal; it can never send) → closed by a person. Tables `evidence.request` (policy as `follow_up_after_days`, `follow_up_max_count`), `evidence.request_item`, `evidence.portal_token`, all with forced RLS. The seed reset and operator purge (`purgeSyntheticEvidence`) delete requests with the evidence. Created, sent and closed are audited; `EvidenceRequestSent/Opened/Answered/Quiet.v1` are written to the outbox (no queue until the follow-up consumer, AIV-P1-040).
- **Skill signals (AIV-P1-072):** the read job also scans the repository for skill signals (`src/domain/skill-signals/`, ported, MIT, see `THIRD_PARTY_NOTICES.md`): source extensions, Dockerfiles, compose files and workflows from the file list, plus at most 15 files of up to 64 KB (root README, dependency manifests, container configs), read in memory and dropped. Vendored, built, hidden and minified paths are never read or counted; code under test, example or fixture folders, `.d.ts`, manifests and README mentions are declaration-level. Signals (path, kind, weight, a detail of at most 160 characters, no file contents) go to `evidence.repository_skill_signal`; `repository_read.files_inspected` and `coverage_gap` (`unreadable | rate_limited | truncated_listing | file_cap | oversized_file`) record coverage. A rate limit during the file reads keeps the commit measurements, records `rate_limited` and schedules a retry that reads only the files again.
- **Grades and freshness (AIV-P1-072):** `requestRepositoryRefresh(ctx, candidateId, jobId)` queues `RepositoryRefreshRequested.v1`; the worker job `evidence.repository.refresh-stale` (`createRepositoryRefreshHandler`, with the jobs module's `createApprovedRubricReads`) re-reads each source that is stale (`isStale`: checked more than 30 days ago, or pushed to since; one metadata call per source) and emits `EvidenceRecorded.v1` again, then grades every read source against the job's approved rubric version: the target skills are the vocabulary skills named in each competency's name or evidence expected. `evidence.repository_skill_grade` holds `STRONG | PARTIAL | NO_EVIDENCE | UNABLE_TO_VERIFY` per source, rubric version, competency and skill, with a reason code and up to six citations; `listRepositorySkillGrades(ctx, candidateId, rubricVersionId)` reads them. Copy: `evidence.skillGrade.*` ("Not found in the {n} files inspected. This is not evidence the skill is missing.", "Could not check: {reason}."). NO_EVIDENCE and UNABLE_TO_VERIFY are never a negative signal; AIV-P1-027 turns them into evidence gaps, and the pack page (AIV-P2-011, #125) enqueues the refresh before a hiring owner decides from a pack.
- **Budget and names (AIV-P1-089, AIV-P1-090):** a spent daily AI budget sets a CV parse to `waiting` and schedules it (and evidence mapping) for 00:05 UTC the next day; `InvalidCitation`, `SchemaMismatch`, `UncitedOutput` and `SourceTooLong` end a CV parse `unreadable` and dead-letter mapping on the first delivery (`PermanentFailure`). **Order and size (AIV-P2-062):** a mapping run takes a transaction advisory lock per workspace, candidate and job without waiting; a run that finds another in flight is rescheduled 60 s later (`MappingBusy`), so the run claimed last is the newest. A source over 60,000 characters, or past the call's 240,000 total, is not sent and never truncated; its id is kept on the run as `too_long_source_ids`. **Uncited links (AIV-P1-156):** a link whose quote is not in its source is dropped by the citation contract and the rest of the answer kept; the run stores the count as `uncited_link_count` (never the quote), so the profile can say lines could not be cited. An unnamed applicant is named from the CV by `nameFromCv` (first lines, local) before any text goes to the model; no name found means the CV is not sent. The rename is audited as the system (`candidate.renamed`).
- **CV parsing (AIV-P1-025):** `requestCvParse(ctx, { candidateId, fileId, synthetic })` stores a pending `cv` source (label "CV", the files module's id as `blob_file_id`) and `evidence.cv_parse` (`pending | parsed | unreadable | failed`), and writes `CvParseRequested.v1` for the `evidence` queue. **Every arriving CV (AIV-P1-079):** the `evidence.application.received` job also calls `queueCvParse` (the system path `requestCvParse` authorises into) for each file of the arrival whose purpose is `cv` (`readFilePurposeAsSystem` of `@credalent/files`), for the arrival's own person only; `evidence` and `portal` files are not parsed. `source_cv_file_key` (workspace, candidate, `blob_file_id`, kind `cv`) with ON CONFLICT DO NOTHING keeps one source, one parse and one event per candidate and file, through redeliveries, repeated arrivals and concurrent deliveries; a second request returns the first `sourceId`. `createFileReadHandlers` gives the worker jobs: `evidence.cv.parse`, and on `FileClean.v1` the parses that waited for the malware scan (a file in quarantine is never read); `FileRejected.v1` marks them unreadable. The job checks the magic bytes, reads text and layout with Document Intelligence's `prebuilt-layout` (`styleFont`; REST with the worker's Entra token; a timeout, throttling or outage rethrows, so the consumer backs off and redelivers while the parse stays `pending` ("Reading the CV…", no retry offered); on the last delivery (`delivery.last` from the consumer, AIV-P1-134) it records `failed` "We could not read this CV. Try again." in its own transaction and the message dead-letters. **Retry (AIV-P1-134):** `retryCvParse(ctx, sourceId)` (admins and recruiters) sets a `failed` parse (or one shown failed because it is still `pending` 30 minutes after it was asked for, `PARSE_GIVE_UP_MS`, AIV-P1-165) back to `pending` by compare-and-set, stamping `cv_parse.requested_at`, and writes `CvParseRequested.v1` for the same source with a dedupe key of its own (never a new source); anything else is `EvidenceError('not_retryable')`, so a second retry writes nothing, and another workspace's source is `cv_not_found`. Audited `evidence.retried`; no text, or a file Document Intelligence calls invalid content, is `unreadable` "Could not be read automatically"), asks `evidence.parseCv` of `@credalent/ai` for roles, skills and statements under the citation contract (a statement citing text not in the CV is dropped and logged as a citation failure), then runs the repair passes in `src/domain/cv.ts` (months restored near the role's line, skills restored from a list line the model anchored twice; adapted from Resume-Matcher, Apache-2.0, see `THIRD_PARTY_NOTICES.md`). Every item is a slice of the CV text, "Claim awaiting validation" and Claim only, cited "page N". Anything inside text aimed at the AI is dropped; excerpts holding an email or phone are dropped and the CV's own contact details go to the candidate record only, as display contact and never as matching identifiers, so a referee's or planted address cannot merge another applicant into this person (`createContactRecorder` of `@credalent/candidates`). "Unusual content in this source" notes (`detectUnusualContent`, plus `hidden_text` from the layout: colour near a background Document Intelligence reports, never an assumed white one, or under 4 pt) are stored in `evidence.source_note` and returned by `getCvParse(ctx, sourceId)`; they change no score, strength or stage, and telemetry carries only their count (`credalent.evidence.unusual_count`). Copy: `evidence.cvStatus.*`, `evidence.unusualContent.*`. **Identifiers (AIV-P1-080):** `createFileReadHandlers` and `createEvidenceMappingHandlers` take `readPerson` (`readPersonAsSystem` of `@credalent/candidates`) and pass the candidate's name, emails and phones with every evidence prompt; `@credalent/ai` replaces them before the call (ADR-006 point 7; `evidence.parseCv` keeps the CV's emails and phones, never the name), and the model's `[CANDIDATE]` is put back as the display name in text a recruiter sees. No person, no call (`MissingIdentifiers`). Showing them on the Candidate screen: AIV-P1-045.
- **Documents (AIV-P1-028):** `requestDocumentRead(ctx, { candidateId, fileId, label, synthetic })` stores a pending `document` source (the given label, such as "Requirements document") for an `evidence` or `portal` upload and `evidence.document_read` (`pending | read | unreadable | failed`), and writes `DocumentReadRequested.v1` for the `evidence` queue. The worker job `evidence.document.read` (in `createFileReadHandlers`, sharing CV parsing's `FileClean.v1` and `FileRejected.v1` handlers, so a file in quarantine or infected is never read) checks the magic bytes (PDF, PNG, JPEG, Word, PowerPoint, Excel), reads text and layout with Document Intelligence, and stores one item per page with text: "Candidate-submitted", Medium (real work, authorship unclear), cited "page N" (the screen shows "<label>, page N"), with the limit "<label> supplied, authorship unverified." until a second source confirms it (AIV-P1-029). No model reads the text here. "Unusual content in this source" notes (`detectUnusualContent` and the CV parse's `hidden_text` layout check) go to `evidence.source_note` and `getDocumentRead(ctx, sourceId)`; the flagged text is cut out of the items, so mapping reads the document as if it were not there. The text's fingerprint is stored once (a finished read is never read again) and checked for another applicant's near-duplicate (`flagCrossApplicantCopies`). Nothing is embedded: the search index waits for the search ticket, which redacts identifiers first (AIV-P1-088). A Document Intelligence outage writes the read `failed` in its own transaction (it comes before the read's row is written, so it never waits on the delivery's locks) and the delivery is retried. Telemetry: the `evidence document read` span carries `credalent.evidence.unusual_count` only.
- **GitHub profiles in a CV (AIV-P1-112):** `parseCv` stores one pending `evidence.profile_expansion` per candidate and profile link (`profileLogins`: at most 2, never a GitHub site path, never inside text aimed at the AI or hidden in the file) and writes `GitHubProfileExpandRequested.v1` (opaque ids; the login stays in the row). The worker job `evidence.github.profile-expand` (`createProfileExpansionHandler`) asks GitHub for the account type (`GET /users/{login}`) and one page of its own repositories (`GET /users/{login}/repos?type=owner&sort=pushed&per_page=30`), and for a `User` queues an ordinary repository read for the newest-pushed public repositories that are not forks, archived or empty, at most 5 per candidate, a repository already linked directly skipped. Reads carry `via = 'cv_profile'` and no login, so they stay "Authorship unclear" (a profile in a CV is the candidate's own unverified statement; the owner decided on 24 Nov 2026 that it does not lift the cap). Source chip suffix: `evidence.sourceVia.cv_profile`. An organisation or a 404 settles `not_expandable`; a rate limit reschedules the job at the reset. Only CV parsing finds profile links: application links and uploaded write-ups do not.
- **Links (AIV-P1-077):** `requestLinkRead(ctx, { candidateId, url, label, synthetic })` stores a pending `shipped_product` source (a shipped product page, published write-up, case study or design share link; the given label) and `evidence.link_read` (`pending | read | not_reachable | failed`, the link as supplied, the page title), once per candidate and link, and writes `LinkReadRequested.v1` for the `evidence` queue. Every non-repository link on an arrival is queued the same way under the label "Linked work" (`queueArrivalReads`). The worker job `evidence.link.read` (`createLinkReadHandler`) fetches it through `src/infrastructure/linkFetch.ts`, the SSRF guard: https only, no `user:pass@`, every address the host resolves to checked against private, loopback, link-local (incl. 169.254.169.254), CGNAT, multicast, unspecified, documentation, the Azure platform endpoint 168.63.129.16, NAT64, 6to4, Teredo, SIIT and IPv4-mapped forms (`isRefusedAddress`, `node:net` BlockList) before connecting, the connection pinned to the checked address (TLS still verifies the host name), every redirect hop checked the same way and at most 3 followed, robots.txt asked for each origin (`CredalentBot`, RFC 9309; a 5xx robots.txt refuses; patterns matched in linear time, never as a regular expression), 10 s in total, `text/html` only, at most 2 MB read while streaming, no screenshots. Anything refused or failing is `not_reachable` ("We could not open this link" beside the URL) and nothing is scored. A page gives its title and readability-style text (`extractPage`, one linear pass, so a hostile 2 MB page cannot stall the worker) as one item, "Candidate-submitted", Medium, cited by the label alone, limit "<label> supplied, authorship unverified."; `detectUnusualContent` notes go to `evidence.source_note` (no page) and their text is cut out of the item. The text is fingerprinted once, as for documents, and not embedded (AIV-P1-088). Nothing writes `failed` any more (no transient call is left in a link read); only rows from before AIV-P1-088 can hold it, and a redelivery reads them again. Telemetry: the `evidence link read` span carries `credalent.evidence.unusual_count` only. The synthetic purge deletes link reads and every `evidence`-owned search vector (`removeModuleVectors`).
- **Duplicate merge (AIV-P1-018):** `createEvidenceRecords(now)` from the composition (unauthorised; apps wire it into `createCandidates`) counts, moves and restores a person's evidence. Every foreign key `(workspace_id, source_id, candidate_id)` to `evidence.source` is `ON UPDATE CASCADE` (migration 0028), so moving a source moves its items, reads, notes and flags; merged pull requests follow their item. Each source moves in a savepoint: one that would break a uniqueness rule (the survivor already holds that link, repository or pull request, or a near-duplicate flag joins the two people's sources) stays with the merged record, which keeps it. Open evidence requests move unless the survivor has one open for the job. Mapping runs and assessment results stay as history; `EvidenceRecorded.v1` is written for the survivor (and both people on undo) so they are mapped and assessed again. `evidence.comparison` rows also stay as history and keep the merged person's `candidate_id`: the survivor's next mapping run writes its own.
- **Interviewer's summaries (AIV-P1-115):** `recordInterviewSummary(ctx, { candidateId, jobId, writtenAt, items, synthetic })` stores what a person confirmed from a meeting summary as an `interview_note` source "Interviewer's summary, 24 Nov", one item per changed competency citing its excerpt and linked to that competency: Medium and Candidate-submitted provenance for a strengthening, Claim only for a weakening, with the limit "The interviewer's summary of the interview: their word, not inspected work." The caller names no provenance and any other strength is refused (`strength`), so such an item is never Strong and never corroborated; the evidence mapping run never reads an `interview_note` item that already carries a competency link (a person linked it; an unlinked interview note, such as the dev seed's "Round 1 notes", is mapped like any other source), and an `interview_note` link is never a second origin for corroboration (`corroboratedCompetencies`), so the interviewer's word corroborates nothing; the profile and scorecard show such an item as "Interviewer's word". Anyone who may submit a scorecard on the job (`scorecard.submit`), since the interviewer applies their own summary; the interviews module calls it in the transaction that applies the score change.
- **Not here:** request drafting and sending screens (AIV-P1-038, AIV-P1-039), follow-ups (AIV-P1-040), the portal (AIV-P1-041), the link status and notes on the Candidate screen (AIV-P1-045), mapping evidence to competencies with AI (AIV-P1-027), the AI contradiction comparison (AIV-P1-078), scoring (`@credalent/assessment`, AIV-P1-030).
- **Tests:** invariants in `src/domain/evidence.test.ts`; database scenarios in `tests/integration/src/evidence.test.ts`; CV parsing in `src/domain/cv.test.ts`, `src/domain/cv.golden.test.ts`, `tests/integration/src/cv-parse.test.ts` and, from the arrival on, `tests/integration/src/cv-intake.test.ts` (Document Intelligence answered by msw from `tests/integration/fixtures/document-intelligence/`); documents in `src/domain/document.test.ts` and `tests/integration/src/document-read.test.ts`; corroboration in `src/domain/corroboration.test.ts`, `src/domain/numericCheck.test.ts` and `tests/integration/src/evidence-corroboration.test.ts`.
- **Evidence mapping (AIV-P1-027):** with a model configured, the worker routes `EvidenceRecorded.v1` and `RubricApproved.v1` to the `evidence` queue, where `createEvidenceMappingHandlers` fans each out to one `EvidenceMappingRequested.v1` per candidate and job (the intake module's `createApplicationReads`). The job `evidence.mapping` (`mapEvidence`) does nothing before the job's rubric is approved; otherwise it grades the read repositories against the approved version (stored signals, no GitHub call), shows the model each source's recorded excerpts (only the newest authorship item of a re-read repository) and its skill grades with their file citations, and calls `evidence.mapToCompetency` through `@credalent/ai` (every quote checked by the citation contract). The pure guards in `src/domain/mapping.ts` then decide what is stored, the lowest cap winning: a competency outside the rubric version is refused; a CV-sourced link above Supporting is rejected, never lowered; a claim is capped at Supporting with "A claim until a document or a second source supports it."; a repository is capped by its authorship (`strengthCapOf`: Medium when unmeasured or when no GitHub login was supplied, AIV-P1-087), by the best skill grade for the competency (STRONG → Strong, PARTIAL single code file → Medium, PARTIAL declaration only → Supporting, NO_EVIDENCE and UNABLE_TO_VERIFY → no link) and at Supporting when the quote is a declaration-level signal line; any other kind is capped too (AIV-P1-087: a document, portal submission or shipped product at Medium, a reference call or interview note at Supporting); the level is capped by the strength the link is stored at (Strong 5, Medium 4, Supporting 2), while a claim's level is capped only by its source's caps, since it counts toward nothing but "up to N if claims hold"; the guards never set "Independently corroborated": only the corroboration rules below do (AIV-P1-029). Each run is an `evidence.mapping` row (rubric version, prompt version, model, "What would change this"), its links new items with `item.mapping_id` and their competency links, and its gaps rows of `evidence.evidence_gap` (`not_found | unable_to_verify | no_evidence`, with the scan's coverage); all three under RLS with FORCE. Earlier runs stay for audit; `listEvidenceForCandidate` shows a job only the newest run's items. "What would change this" keeps at most 3 checks, each closing a gap or a capped item, ordered by competency weight times headroom below Strong; a check closing nothing is dropped. `getEvidenceMapping(ctx, candidateId, jobId)` reads the newest run (job-scoped). **Could not assess (AIV-P1-165):** a mapping rejected for good (`PermanentFailure`) or failing on its last delivery is recorded in `evidence.mapping_failure` (workspace, candidate, job; forced RLS) in its own transaction, since the delivery's rolls back; the next run that maps deletes it on its way to commit. `retryMapping(ctx, candidateId, jobId)` (admins and recruiters) deletes it and queues `EvidenceMappingRequested.v1` for that candidate and job only, audited `evidence.retried`; with no failure recorded it is `not_retryable`. `listCvStatuses(ctx, jobId, candidateIds)` gives each candidate's newest CV parse (source, file id, status; a parse still `pending` past `PARSE_GIVE_UP_MS` reads `failed`, since only the last delivery writes `failed` and a lost one would leave it pending for good) and whether their mapping failed, for the ranking and the profile (every role granted the job). The run writes `EvidenceMapped.v1` for the assessment (AIV-P1-031). A gap is never negative evidence and never a reason to reject.
- **Corroboration and contradictions (AIV-P1-029):** after the guards, the mapping run applies the pure rules in `src/domain/corroboration.ts`. A competency's Candidate-submitted links become "Independently corroborated" when they come from at least two origins and at least one is independent of the candidate: a reference call, a measured commit history, or an upstream repository whose pull requests were all merged by another maintainer (`merged_by` is not one of the candidate's supplied logins, and the repository owner is not one of them either). Self-merged pull requests, pull requests into the candidate's own repositories and an unnamed merger never count. CVs, documents, write-ups, portal submissions and interview notes are the candidate's own account, so two of them never corroborate each other, and claims count toward neither. A link from a document, portal submission or shipped product on a competency that is not corroborated is stored as a claim at Supporting, "The candidate's own account: a claim until a second, independent source supports it." (`settleProvenance`, AIV-P1-087), so it counts zero in the backed score; a link in an open contradiction stays listed as "Contradictory" and counts nowhere until a person resolves it; the resolution names which source stands (or both), and a change to that queues a re-map (AIV-P2-063). Near-duplicate sources (`listOriginGroups`, AIV-P1-071) are one origin whatever their kind or title, so a re-upload, or reference notes copied from a write-up, confirms nothing. A source in an open contradiction vouches for nothing until a person resolves it. Corroboration is decided per competency, so every Candidate-submitted link on it is marked (`shortcut:` until AIV-P1-078 can match claims). Published benchmarks and employer records have no source kind yet (`shortcut:`). **Numeric pre-check** (`src/domain/numericCheck.ts`, ported, MIT, see `THIRD_PARTY_NOTICES.md`): for each pair of links on one competency from different origins, two numbers are compared only when they count the same unit (headcount words such as "engineers", "people" and "-person" are one unit; a four-digit year or a function word such as "the" is never a unit) and their sentences share a context word besides the unit (two words for a percentage or a duration). For a headcount the unit noun itself is enough, as the ticket's "12 engineers" against "managed 5 engineers" needs (`shortcut:`). Values are compared per sentence pair and unit, so a shared "30%" never makes "5 engineers" agree with "12 engineers". The same number gives an agreement fact, and a different number a contradiction. **AI comparison (AIV-P1-078):** the pairs it cannot settle (a number stated in words, such as "about 9,000" against "a few hundred") go to the model in one `evidence.compareExcerpts` call per run (`comparePairs` in `src/application/mapping.ts`, prompt versioned in `@credalent/ai`); settled pairs never do, and a pair with no number on either side is not compared (`shortcut:`). A flag must quote both excerpts of one requested pair; an answer citing a source it was not given, quoting text that is not in the excerpt, or failing its schema is rejected whole and no AI contradiction is stored. The run logs `credalent.evidence.compared.sent`, `.flagged` and `.rejected` (pair counts, never excerpt text). Each settled pair and each AI flag is an `evidence.comparison` row (run, competency, both item ids, `agreement | contradiction`, `method` `numeric_precheck | ai`; the AI only flags contradictions), under RLS with FORCE. An AI contradiction is shown, withheld and resolved exactly like a pre-check one; a pair the model flagged once stays a contradiction on every later run without a new call (`aiFlags` by `pairKey`), so only a person's resolution ends it. Excerpts reach the model with the candidate's name, emails and phones replaced by `@credalent/ai` (ADR-006 point 7, AIV-P1-080), as for the mapping prompt. While a contradiction is open, `listEvidenceForCandidate` shows both items as "Contradictory", so the backed score leaves them out (`counts` in `@credalent/assessment`). `listComparisons(ctx, candidateId, jobId)` lists the newest run's comparisons (job-scoped). `resolveContradiction(ctx, comparisonId, { note, limit })` (admins and recruiters) records who, when, the note and the limit both items then state, and writes `evidence.contradiction_resolved` (actor, time, note required) to the audit log as the last statement. A re-map keeps a resolution while the same two excerpts of the same two sources contradict again. Nothing here changes a stage, rejects or contacts anyone. **Reference calls:** `recordReferenceCall(ctx, { candidateId, calledOn, calledRole, notes, synthetic })` (admins and recruiters; anyone else gets `ForbiddenError` and nothing is stored) stores a `reference_call` source labelled "Reference call, 11 Nov", with check method "Reference call (<role>)", and one Supporting, Candidate-submitted item holding the notes. The person called is recorded by role only (`REFERENCE_ROLES`), never by name; the call date must be a real day, not in the future. The notes are fingerprinted. The run logs `credalent.evidence.contradictions` (a count). The entry screen and showing provenance on the profile come in AIV-P1-045. A resolution writes `ContradictionResolved.v1` (candidate, job, the mapping run's rubric version and comparison ids only) to `evidence.outbox` in the same transaction, before the audit entry, and the assessment worker re-scores that candidate for that job (AIV-P1-098).
