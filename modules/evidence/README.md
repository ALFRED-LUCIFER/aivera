# @credalent/evidence

Everything a score can rest on (AIV-P1-024): where a piece of evidence came from, the exact excerpt it cites, its provenance, its strength and what it does not show. Other code imports only `@credalent/evidence` (the `EvidenceContract` types); apps build it with `createEvidence(workspaces, audit, now)` from `@credalent/evidence/composition`.

- **Tables:** `evidence.source` (candidate id, kind `cv | repository | document | shipped_product | reference_call | portal_submission | interview_note`, label, https url or blob file id, `captured_at`, `checked_at` and `check_method` such as "Commit history", `synthetic`), `evidence.item` (source, candidate, excerpt, excerpt span such as "page 2", provenance, strength, `limit_statement`, `synthetic`), `evidence.competency_link` (item, job id, competency id of the jobs module, and the `level` 0–5 the item shows for that competency, 0 until mapped), `evidence.duplicate_flag` (AIV-P1-071) `evidence.repository_read`, `evidence.merged_pull_request`, `evidence.repository_skill_signal` and `evidence.repository_skill_grade` (below), `evidence.inbox` (handled message ids) and `evidence.outbox`. Candidate, job and competency ids are opaque: no foreign key across modules. The foreign key `(workspace_id, source_id, candidate_id)` keeps an item on its own workspace's and candidate's source. Migrations are tracked in `migrations.evidence`.
- **Provenance and strength** are closed lists, with the values `ProvenanceTag` and `StrengthMeter` of `@credalent/ui` take: provenance `corroborated | submitted | claim | contradictory | awaiting-defence`, strength `strong | medium | supporting | claim` (the Rubric page's scoring definitions). Labels: `evidence.provenance.*` and `rubric.strength.*` in `packages/i18n`.
- **Invariants:** a `claim` or `awaiting-defence` item is never stronger than Supporting ("A claim cannot be stronger than Supporting"), and every item states its limit ("State what this evidence does not show"). The domain (`checkItem`) refuses both before anything is written, and check constraints refuse them again for any write path. "Claim only" counting zero is scoring's rule (AIV-P1-030).
- **Contract:** `recordEvidence(ctx, { candidateId, source, items, synthetic })` stores a source, its items and their competency links; `linkToCompetency(ctx, itemId, { jobId, competencyId, level })` adds a link once, at the latest level ("A level is a whole number from 0 to 5"); `listEvidenceForCandidate(ctx, candidateId, jobId)` returns the candidate's items with their source and their links to that job (an empty list when there are none); `getEvidenceItem(ctx, id)`; `purgeSyntheticEvidence(ctx)` for the demo seed's reset.
- **Authorisation:** through the workspaces `authorize`: recording and linking as `candidate.create`, reading as `candidate.view` with no job, so admins and recruiters only until applications give a job to check (AIV-P1-017).
- **Row-level security (ADR-005):** every table `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`; the repository also filters by workspace.
- **Event:** `EvidenceRecorded.v1` (the ticket's "evidence.recorded"; `{ candidateId, sourceId, itemIds }`, strict, opaque ids only) is written to `evidence.outbox` in the transaction that records the evidence; the relay sends it to the `assessment` queue.
- **Personal data (AGENTS.md 1.2):** labels, urls, excerpts and limits are candidate personal data (`PERSONAL_DATA_FIELDS`). The module never logs; `EvidenceError` never repeats the refused value.
- **Fingerprints (AIV-P1-071):** `recordEvidence` takes an optional `text` (a write-up's or document's prose) and stores only its 64-bit SimHash as `source.text_fingerprint` (16 hex characters, check constraint), never the text. `domain/fingerprint.ts` (ported, MIT, see `THIRD_PARTY_NOTICES.md`) normalises the text, drops CV boilerplate (contact details, lines of up to three words, heading lines, short lists such as "Python, SQL, Docker"), and gives no fingerprint below `FINGERPRINT_MIN_TEXT` (200 normalised characters); no fingerprint never matches. Near-duplicate means similarity (1 − differing bits/64) at least `NEAR_DUPLICATE_THRESHOLD` (0.92).
- **Origins and flags:** `listOriginGroups(ctx, candidateId)` groups one candidate's near-duplicate sources into one origin (for AIV-P1-029). When another candidate's source in the same workspace is a near-duplicate, `recordEvidence` writes an `evidence.duplicate_flag` ("Also submitted by another applicant") citing both sources by id; `listDuplicateFlags(ctx, candidateId)` returns the flags on either side. A flag changes no score, rank, stage or contact. `resolveDuplicateFlag(ctx, flagId, reason)` (`shared_group_project | same_template | needs_follow_up`, labels `evidence.duplicate.*`) is admins and recruiters only (`candidate.create`) and audited as `evidence.flag_resolved`, last. Comparisons take a per-workspace advisory lock until commit, so two copies recorded at once still flag each other. The raised flag is logged with the flag and source ids and `credalent.evidence.similarity` only. Showing the flag on the candidate profile is the profile tickets' (AIV-P1-043 #107, AIV-P1-045 #109).
- **GitHub repositories (AIV-P1-026):** `requestRepositoryRead(ctx, { candidateId, url, githubLogin, emails, synthetic })` stores a pending `repository` source for a public `https://github.com/<owner>/<repo>` link, the login and emails in `evidence.repository_read`, and writes `RepositoryReadRequested.v1` (opaque ids) for the `evidence` queue. The worker job `evidence.repository.read` (`createRepositoryReadHandler`, a GitHub App installation token, every answer zod-checked) reads metadata, languages, last push, the file list (tests and CI presence; no contents) and the commit list. **Authorship rules** (`src/domain/repository.ts`): a commit is the candidate's only by login, a supplied email or a Co-authored-by trailer, never by owning the repository; a fork gets status `fork` and nothing is measured or scored; a 404 or private repository gets `not_accessible`; commits that only touch lockfiles, vendored or built paths are counted apart and left out of the share (`getRepositoryRead` gives the share, its class `clear | shared | minor` and the strength cap: Strong only when clear). The item reads "authored 412 of 460 commits, 38 only touch generated files" and is at most Medium (a second source is AIV-P1-029); the source is checked by "Commit history". Pull requests the candidate authored and merged into repositories they neither own nor forked are items of their own in `evidence.merged_pull_request` (repository, number, merged date, `merged_by`, `self_merged`), never added to the commit count. A spent rate limit schedules the request on Service Bus for after `x-ratelimit-reset`; the source stays pending. **One read per link (AIV-P1-076):** a link is stored as `https://github.com/<owner>/<repo>` lower case, without `.git`, trailing slash, query or fragment, and `repository_read_candidate_url_key` (workspace, candidate, URL) keeps one read per candidate and repository, concurrent requests included; a second request returns the first `sourceId` and writes no second event. The worker job `evidence.application.received` (`createApplicationReceivedHandler`, fed by the intake and candidates system reads from the worker) consumes `ApplicationReceived.v1` and queues a read for each GitHub repository link on the arrival or a member's link (`queueArrivalReads`); other links stay on the application. Identity is only what the candidate supplied: their login (an invalid one is dropped, never guessed) and the emails on their record. With no login (`github_login` null) commits match by email only, no merged pull requests are searched, the item's limit starts "Authorship unclear: no GitHub login supplied." and the cap is Medium. Logs carry the source and candidate ids only. CV parsing (AIV-P1-025) calls `queueRepositoryRead` for each repository URL it finds. Caps (`shortcut:`): generated-only check on the newest 300 authored commits, commit list 5,000, first 100 merged pull requests. Statuses' copy: `evidence.repositoryStatus.*` in `packages/i18n`.
- **Evidence requests (AIV-P1-037):** `createDraftRequest(ctx, { candidateId, jobId })` makes a draft naming only the candidate's open claims for the job (one line per competency, from items resting on "Claim awaiting validation" or "Awaiting live defence"; "Nothing rests on a claim for this job" when there are none), with the default follow-up policy (after 2 days, at most twice). One open request per candidate per job (partial unique index, mapped to "This candidate already has an open request for this job"). Status moves are compare-and-set, so racing moves cannot skip the table. Open claims come from the candidate's evidence items, not the assessment snapshot: evidence cannot depend on assessment (assessment reads evidence), so a claim on a competency outside the approved rubric, or one already proven by other work, still appears; the request screen (AIV-P1-038), which can read both, narrows it. State machine (`domain/request.ts`): draft → sent only by a person (`sendRequest`, which issues the portal token and returns it once; only its SHA-256 is stored, valid 30 days) → opened → answered | quiet, recorded by the system (`createRequestOutcomeRecorder` from the composition: a workspace-scoped transaction with no member, for the follow-up worker and the portal; it can never send) → closed by a person. Tables `evidence.request` (policy as `follow_up_after_days`, `follow_up_max_count`), `evidence.request_item`, `evidence.portal_token`, all with forced RLS. The seed reset and operator purge (`purgeSyntheticEvidence`) delete requests with the evidence. Created, sent and closed are audited; `EvidenceRequestSent/Opened/Answered/Quiet.v1` are written to the outbox (no queue until the follow-up consumer, AIV-P1-040).
- **Skill signals (AIV-P1-072):** the read job also scans the repository for skill signals (`src/domain/skill-signals/`, ported, MIT, see `THIRD_PARTY_NOTICES.md`): source extensions, Dockerfiles, compose files and workflows from the file list, plus at most 15 files of up to 64 KB (root README, dependency manifests, container configs), read in memory and dropped. Vendored, built, hidden and minified paths are never read or counted; code under test, example or fixture folders, `.d.ts`, manifests and README mentions are declaration-level. Signals (path, kind, weight, a detail of at most 160 characters, no file contents) go to `evidence.repository_skill_signal`; `repository_read.files_inspected` and `coverage_gap` (`unreadable | rate_limited | truncated_listing | file_cap | oversized_file`) record coverage. A rate limit during the file reads keeps the commit measurements, records `rate_limited` and schedules a retry that reads only the files again.
- **Grades and freshness (AIV-P1-072):** `requestRepositoryRefresh(ctx, candidateId, jobId)` queues `RepositoryRefreshRequested.v1`; the worker job `evidence.repository.refresh-stale` (`createRepositoryRefreshHandler`, with the jobs module's `createApprovedRubricReads`) re-reads each source that is stale (`isStale`: checked more than 30 days ago, or pushed to since; one metadata call per source) and emits `EvidenceRecorded.v1` again, then grades every read source against the job's approved rubric version: the target skills are the vocabulary skills named in each competency's name or evidence expected. `evidence.repository_skill_grade` holds `STRONG | PARTIAL | NO_EVIDENCE | UNABLE_TO_VERIFY` per source, rubric version, competency and skill, with a reason code and up to six citations; `listRepositorySkillGrades(ctx, candidateId, rubricVersionId)` reads them. Copy: `evidence.skillGrade.*` ("Not found in the {n} files inspected. This is not evidence the skill is missing.", "Could not check: {reason}."). NO_EVIDENCE and UNABLE_TO_VERIFY are never a negative signal; AIV-P1-027 turns them into evidence gaps, and AIV-P2-010 enqueues the refresh before a decision pack.
- **Not here:** request drafting and sending screens (AIV-P1-038, AIV-P1-039), follow-ups (AIV-P1-040), the portal (AIV-P1-041), CV parsing (AIV-P1-025), documents and links (AIV-P1-028), mapping evidence to competencies with AI (AIV-P1-027), corroboration rules (AIV-P1-029), scoring (`@credalent/assessment`, AIV-P1-030).
- **Tests:** invariants in `src/domain/evidence.test.ts`; database scenarios in `tests/integration/src/evidence.test.ts`.
- **Evidence mapping (AIV-P1-027):** with a model configured, the worker routes `EvidenceRecorded.v1` and `RubricApproved.v1` to the `evidence` queue, where `createEvidenceMappingHandlers` fans each out to one `EvidenceMappingRequested.v1` per candidate and job (the intake module's `createApplicationReads`). The job `evidence.mapping` (`mapEvidence`) does nothing before the job's rubric is approved; otherwise it grades the read repositories against the approved version (stored signals, no GitHub call), shows the model each source's recorded excerpts (only the newest authorship item of a re-read repository) and its skill grades with their file citations, and calls `evidence.mapToCompetency` through `@credalent/ai` (every quote checked by the citation contract). The pure guards in `src/domain/mapping.ts` then decide what is stored, the lowest cap winning: a competency outside the rubric version is refused; a CV-sourced link above Supporting is rejected, never lowered; a claim is capped at Supporting with "A claim until a document or a second source supports it."; a repository is capped by its authorship (`STRENGTH_CAP`; Medium when unmeasured), by the best skill grade for the competency (STRONG → Strong, PARTIAL single code file → Medium, PARTIAL declaration only → Supporting, NO_EVIDENCE and UNABLE_TO_VERIFY → no link) and at Supporting when the quote is a declaration-level signal line; nothing is stored as "Independently corroborated" (AIV-P1-029). Each run is an `evidence.mapping` row (rubric version, prompt version, model, "What would change this"), its links new items with `item.mapping_id` and their competency links, and its gaps rows of `evidence.evidence_gap` (`not_found | unable_to_verify | no_evidence`, with the scan's coverage); all three under RLS with FORCE. Earlier runs stay for audit; `listEvidenceForCandidate` shows a job only the newest run's items. "What would change this" keeps at most 3 checks, each closing a gap or a capped item, ordered by competency weight times headroom below Strong; a check closing nothing is dropped. `getEvidenceMapping(ctx, candidateId, jobId)` reads the newest run (job-scoped). The run writes `EvidenceMapped.v1` for the assessment (AIV-P1-031). A gap is never negative evidence and never a reason to reject.
