# @aivera/ops

Platform settings the operators change from the console (AIV-P2-039, [ADR-012](../../docs/adr/ADR-012-operator-console.md) point 9). Other code imports only `@aivera/ops` (the `OpsSettingsContract` types); apps build it with `createOpsSettings(db, audit)` from `@aivera/ops/composition`. No module that ranks or assesses may import it (architecture rule `paying-never-changes-ranking`, AGENTS.md 1.8).

- **Table (schema `ops`, tracked in `migrations.ops`):** `platform_setting`, one row keyed on the constant `true` (`platform_setting_single_row`), holding `approval_required` (whether a sign-up's workspace waits for an operator), `updated_by` (the operator's identity user id) and `updated_at`. Migration `0001_settings_row` inserts the row with the pilot default, on. It is not workspace-owned and holds no personal data, so it has no tenant policy (`tests/integration/src/tenancy.test.ts` `GLOBAL_TABLES`).
- **Contract:** `approvalRequired()` (sign-up reads it on every new workspace) and `setApprovalRequired({ operatorId, required, reason })`, which locks the row, refuses a value it already has (`OpsError('unchanged')`) or a reason under 10 characters (`reason_required`), writes it and, last in the same transaction, records `ops.approval_mode_changed` with the value before and after and the reason in the platform audit log. Changing the switch approves or rejects nothing: workspaces already waiting stay waiting. Callers check the `platformOperator` policy first (`apps/web/src/server/operator.ts`).
- **Tests:** `src/application/settings.test.ts`; the database scenarios in `tests/integration/src/ops-approvals.test.ts`.
