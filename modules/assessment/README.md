# @credalent/assessment

The scoring core (AIV-P1-030): a candidate's mapped evidence and a job's approved rubric version in, the backed score, the claim range and a level per competency out. Other code imports only `@credalent/assessment`; apps build it with `createAssessment(workspaces, audit, jobs, now, candidateJob, applicants, explain)` from `@credalent/assessment/composition`, and the worker registers `createAssessmentHandlers` on the `assessment` queue.

- **`assess(rubric, links)`** is pure and deterministic (`src/domain/assess.ts`). Per competency:
  - **Proven level (0–5):** the highest level among items that count: Strong or Medium work that is `corroborated` or `submitted`, and Supporting only when `corroborated`. Claims, contradicted items and items awaiting live defence never count (AGENTS.md 1.6).
  - **Claimed level:** the highest level of any linked item that is not contradicted, never below the proven level. A contradicted item widens nothing: a second source said otherwise.
  - **Citations:** a proven level above 0 always lists the item ids it rests on; the type `Proven` makes an uncited level impossible.
- **Scores:** backed = Σ weight × proven level ÷ 5, rounded (0–100); "up to N if claims hold" = the same with claimed levels. Owner decision, 20 Nov 2026: the formula wins over the design's illustrative numbers, so Sara Al Qahtani scores 63 up to 83 on the Senior AI Engineer rubric version 2.
- **Also:** "meets the job's need on X of N" (proven ≥ level needed), `missingCritical` (mandatory competencies proven below the need: evidence to request, never a reason to reject), and confidence from the share of weight whose proven level a Strong item reaches (High from 60%, Medium from 30%, else Low).
- **What reaches the score:** per link only the item id, competency, level, strength and provenance (`toLinks`), and only the assessed candidate's items. Anything else on an item or its source, such as an "Unusual content in this source" note, is dropped, so it never acts on the candidate (AGENTS.md 1.5).
- **Tables:** `assessment.result`, one row per assessment that changed something: the score history of a candidate for a job. Ids, levels and numbers only. `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy`; the app role cannot update a row (history) but can delete (erasure). Check constraints keep the backed score within 0–100 and at most the upper bound. `assessment.inbox` holds the handled message ids of the consumers below (RLS with FORCE). `assessment.interview_change` holds a person's applied interview changes (competency, interview id, strength, level, the items a weakening names, reason, who and when, idempotency key, preview id): RLS with FORCE, append-only for the app role, deleted with its result.
- **Contract:** `assessCandidate(ctx, { candidateId, jobId, rubric, evidence })` stores the result when it differs from the latest and audits every stored result (`score.changed`, the last write; before and after hold the stored result id, the rubric version, scores, meets-need, confidence and each competency's proven level); `getLatestAssessment(ctx, candidateId, jobId)`. Admins and recruiters (`candidate.create`, `candidate.view`). Nothing is rejected, advanced or sent.
- **Ranking (AIV-P1-031):** `listRanking(ctx, jobId)` is `{ status: 'awaiting_rubric' }` until the job has an approved rubric version, then `{ status: 'ranked', rubricVersionId, rows }`: each candidate's latest result on that version, by backed score, then upper bound, then the candidate's first assessment for the job (`shortcut:` for "earliest application", which is intake's), ranked from 1 at read. A candidate not yet assessed on the approved version is not listed; nobody is hidden or rejected by rank. `candidate.view` on the job: admins and recruiters, hiring owners and interviewers on a granted job only; a job the context cannot see throws `ForbiddenError`.
- **The ranked table (AIV-P1-034):** the web app's Candidates tab joins `listRanking` to intake's `listApplicationsForJob` by person id; applicants with no result on the approved version stay listed as "Not yet scored". It names `missingCritical` competencies through the jobs module's `createApprovedRubricReads`, in the member's transaction and only after `listRanking` authorised the job.
- **On the worker (AIV-P1-031):** `createAssessmentHandlers` consumes `EvidenceMapped.v1` and `ContradictionResolved.v1` (AIV-P1-098: a person resolved a contradiction; that candidate and job, on the event's rubric version), and, only while evidence mapping is off, `RubricApproved.v1` (every applicant of the job) and `EvidenceRecorded.v1` (every job of the candidate). Each reads the job's approved rubric version (the jobs module's `createApprovedRubricReads`; none approved, nothing is assessed, never a draft) and the candidate's evidence for the job (`readEvidenceForJobAsSystem`), and stores and audits a result only when it changed, as the system, in the envelope's workspace transaction, once per message id (`assessment.inbox`). A mapping made against a version that is no longer approved is skipped: the new version's mapping follows. A per-candidate-and-job advisory lock, taken before the evidence is read and in id order across a fan-out, serialises concurrent runs, so an older read never stores after a newer one. In a multi-candidate run each candidate's audit entry is the last write for that candidate, and the whole run commits or rolls back together. No `assessment.changed` event yet: nothing consumes one (`shortcut:` in `src/application/worker.ts`).
- **Paying never changes ranking:** the module imports nothing from billing, portfolio or ops (architecture rule `paying-never-changes-ranking`), nor from candidate-accounts (`recruiter-side-no-candidate-accounts`).
- **Ranking explanation (AIV-P1-033):** `explainRanking(ctx, candidateId, jobId)` gives up to three statements on the latest snapshot, each citing a snapshot fact (`itemId` null) or an evidence item with the exact words quoted. The facts (`src/domain/explain.ts`) are the weight resting on independently checked work (a corroborated item among those the proven level cites) and the weight still resting on claims; the model (`assessment.explainRanking` in `@credalent/ai`) reads the facts with placeholders in them (`{checkedWeight}`, `{claimNames}`, ...) and writes those placeholders; the schema rejects a percent sign, a number word or an unknown placeholder, so every number of the score is filled from the snapshot, in the statement and in a quote of the facts. A figure of the candidate's work ("412 of 460 commits", "p95") may stand in a statement only when the statement quotes it from the evidence excerpt it cites (AIV-P1-132, owner decision 24 Nov 2026); a figure in the facts never counts. A statement with no citation, or a placeholder the snapshot has no fact for, is dropped; a rejected answer, an unavailable model or an exhausted token budget returns a template from the same facts with `source: 'template'` ("Summary generated without AI"). Cached per snapshot id and prompt version in `assessment.explanation` (AI answers only; RLS with FORCE). `candidate.view` on the job, as `getLatestAssessment`. The profile that shows it is AIV-P1-043; assistant questions about ranking are AIV-P2-028.
- **Interview-based score changes (AIV-P1-117):** one command the scorecard (AIV-P2-004 to AIV-P2-006) and the meeting summary (AIV-P1-115) both end in. `previewScoreChange(ctx, { assessmentId, interviewId, changes: [{ competencyId, rating }] })` writes nothing and returns each changed competency's strength and proven level before and after, the backed score and upper bound, and a `previewId`. `applyScoreChange(ctx, { ...same, previewId, reason, idempotencyKey })` runs the same computation under the candidate-and-job lock and stores one new snapshot, the changes (`assessment.interview_change`) and one `score.changed` audit entry per changed competency (actor, time, the reason as the note, strength, proven level and backed score before and after, the rating and the interview id), the audit entries last. It changes no stage and contacts nobody.
  - **Rating to strength** (`src/domain/scoreChange.ts`): Not shown, the competency's present evidence counts as Claim only (zero in the backed score; the claim range stays), except work a second source checked (`corroborated`), which one interviewer's word never overrides, and evidence added later; Partly shown, no change; Clearly shown, the interview is added as Medium evidence; Strongly shown, as Strong. A shown rating never weakens stronger work already there. There is no second formula: a change only alters the links `assess` scores, and `recordAssessment` re-applies the stored changes on every later run on the same rubric version.
  - **The level an interview backs:** the level the job needs for the competency, whatever the candidate claimed: an uninspected claim never sets a backed level (AGENTS.md 1.6), so the same rating gives two candidates the same proven level. The numbers follow the formula, not the scorecard artboard's illustrative ones (55 to 61).
  - **Several interviews:** the latest change per competency and interview stands. A later interview never removes what another interview showed, whatever it rates; the same interview rated again replaces its own change.
  - **The interviewer's word:** the interview is cited by its id as its own source, scored like submitted work (`INTERVIEW_PROVENANCE`) and labelled `interviewer_word`: the candidate submitted nothing, so it is not shown as "Candidate-submitted". It is never corroborated, corroborates nothing beside it (a CV claim stays a claim) and never counts as independently checked work in `explainRanking`.
  - **Refused, storing nothing:** `stale` ("Preview the change again") unless the snapshot is still the latest and `previewId` is what the preview returns now; `not_yet_scored` while the evidence holds something the snapshot has not scored; `interview_not_held` for a `scheduled` or `cancelled` interview (`shortcut:` `to_schedule` counts as held, because the pilot does not schedule); `competency_not_in_interview` for a competency the interview does not investigate; `competency_not_in_rubric`; `source_not_found`.
  - **Repeated:** the same idempotency key with the same preview and reason returns the snapshot stored the first time and writes nothing (a unique index backs it); with another preview or reason it is `idempotency_conflict`. Ratings that change nothing store nothing.
  - **Who:** preview `candidate.view`, apply `scorecard.submit`, both on the snapshot's stored job (the candidate's application, through `candidateJob`); a snapshot of another workspace is refused as one that does not exist. The interview must be one the context can see, of the same candidate and job (`interviewOf`, the interviews contract's `getInterview`): the caller's composition root wires it with `evidenceForJob` as `createAssessment`'s last argument. No app wires it yet: the first screen that calls it does (AIV-P2-004, AIV-P1-115).
  - **Known limits (`shortcut:` in the code):** changes are keyed by competency id, which belongs to one rubric version, so a newly approved version scores without them; nothing reads the stored changes yet, so a screen cannot tell a cited interview id from an evidence item id or show its limit (AIV-P2-006 adds the read); a candidate merged into another keeps their changes on the old id.
- **Not here:** the scorecard page and its submit (AIV-P2-004 to AIV-P2-006), the meeting-summary mapping (AIV-P1-115), per-question points, and recording the interview note through the evidence contract.
- **Tests:** the explanation in `src/application/explain.test.ts` (and the eval set `packages/ai/evals/assessment.explainRanking/`); rules, the claims-never-count property and determinism in `src/domain/assess.test.ts`; the note and the ranking order in `src/application/assessment.test.ts`; interview-based changes in `src/domain/scoreChange.test.ts` and `tests/integration/src/score-change.test.ts`; database scenarios in `tests/integration/src/assessment.test.ts`; the worker and ranking scenarios in `tests/integration/src/assessment-worker.test.ts`.
