# @credalent/assessment

The scoring core (AIV-P1-030): a candidate's mapped evidence and a job's approved rubric version in, the backed score, the claim range and a level per competency out. Other code imports only `@credalent/assessment`; apps build it with `createAssessment(workspaces, audit, jobs, now)` from `@credalent/assessment/composition`, and the worker registers `createAssessmentHandlers` on the `assessment` queue.

- **`assess(rubric, links)`** is pure and deterministic (`src/domain/assess.ts`). Per competency:
  - **Proven level (0–5):** the highest level among items that count: Strong or Medium work that is `corroborated` or `submitted`, and Supporting only when `corroborated`. Claims, contradicted items and items awaiting live defence never count (AGENTS.md 1.6).
  - **Claimed level:** the highest level of any linked item that is not contradicted, never below the proven level. A contradicted item widens nothing: a second source said otherwise.
  - **Citations:** a proven level above 0 always lists the item ids it rests on; the type `Proven` makes an uncited level impossible.
- **Scores:** backed = Σ weight × proven level ÷ 5, rounded (0–100); "up to N if claims hold" = the same with claimed levels. Owner decision, 20 Nov 2026: the formula wins over the design's illustrative numbers, so Sara Al Qahtani scores 63 up to 83 on the Senior AI Engineer rubric version 2.
- **Also:** "meets the job's need on X of N" (proven ≥ level needed), `missingCritical` (mandatory competencies proven below the need: evidence to request, never a reason to reject), and confidence from the share of weight whose proven level a Strong item reaches (High from 60%, Medium from 30%, else Low).
- **What reaches the score:** per link only the item id, competency, level, strength and provenance (`toLinks`), and only the assessed candidate's items. Anything else on an item or its source, such as an "Unusual content in this source" note, is dropped, so it never acts on the candidate (AGENTS.md 1.5).
- **Tables:** `assessment.result`, one row per assessment that changed something: the score history of a candidate for a job. Ids, levels and numbers only. `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy`; the app role cannot update a row (history) but can delete (erasure). Check constraints keep the backed score within 0–100 and at most the upper bound. `assessment.inbox` holds the handled message ids of the consumers below (RLS with FORCE).
- **Contract:** `assessCandidate(ctx, { candidateId, jobId, rubric, evidence })` stores the result when it differs from the latest and audits every stored result (`score.changed`, the last write; before and after hold the stored result id, the rubric version, scores, meets-need, confidence and each competency's proven level); `getLatestAssessment(ctx, candidateId, jobId)`. Admins and recruiters (`candidate.create`, `candidate.view`). Nothing is rejected, advanced or sent.
- **Ranking (AIV-P1-031):** `listRanking(ctx, jobId)` is `{ status: 'awaiting_rubric' }` until the job has an approved rubric version, then `{ status: 'ranked', rubricVersionId, rows }`: each candidate's latest result on that version, by backed score, then upper bound, then the candidate's first assessment for the job (`shortcut:` for "earliest application", which is intake's), ranked from 1 at read. A candidate not yet assessed on the approved version is not listed; nobody is hidden or rejected by rank. `candidate.view` on the job: admins and recruiters, hiring owners and interviewers on a granted job only; a job the context cannot see throws `ForbiddenError`.
- **The ranked table (AIV-P1-034):** the web app's Candidates tab joins `listRanking` to intake's `listApplicationsForJob` by person id; applicants with no result on the approved version stay listed as "Not yet scored". It names `missingCritical` competencies through the jobs module's `createApprovedRubricReads`, in the member's transaction and only after `listRanking` authorised the job.
- **On the worker (AIV-P1-031):** `createAssessmentHandlers` consumes `EvidenceMapped.v1` (that candidate and job), and, only while evidence mapping is off, `RubricApproved.v1` (every applicant of the job) and `EvidenceRecorded.v1` (every job of the candidate). Each reads the job's approved rubric version (the jobs module's `createApprovedRubricReads`; none approved, nothing is assessed, never a draft) and the candidate's evidence for the job (`readEvidenceForJobAsSystem`), and stores and audits a result only when it changed, as the system, in the envelope's workspace transaction, once per message id (`assessment.inbox`). A mapping made against a version that is no longer approved is skipped: the new version's mapping follows. A per-candidate-and-job advisory lock, taken before the evidence is read and in id order across a fan-out, serialises concurrent runs, so an older read never stores after a newer one. In a multi-candidate run each candidate's audit entry is the last write for that candidate, and the whole run commits or rolls back together. No `assessment.changed` event yet: nothing consumes one (`shortcut:` in `src/application/worker.ts`).
- **Paying never changes ranking:** the module imports nothing from billing, portfolio or ops (architecture rule `paying-never-changes-ranking`), nor from candidate-accounts (`recruiter-side-no-candidate-accounts`).
- **Not here:** the ranked table (AIV-P1-034), explanations (AIV-P1-033), interview score changes (`scorecard.submitted`, AIV-P2-005, AIV-P2-006), re-scoring when a contradiction is resolved (no event carries it yet).
- **Tests:** rules, the claims-never-count property and determinism in `src/domain/assess.test.ts`; the note and the ranking order in `src/application/assessment.test.ts`; database scenarios in `tests/integration/src/assessment.test.ts`; the worker and ranking scenarios in `tests/integration/src/assessment-worker.test.ts`.
