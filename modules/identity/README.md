# @aivera/identity

The identity module (AIV-P0-009, [ADR-009](../../docs/adr/ADR-009-identity-and-account-model.md)). One user per verified email; each sign-in method (the ID token's issuer and subject) maps to that user. Other code imports only `@aivera/identity` (the `IdentityContract` types); apps build it with `createIdentity(db)` from `@aivera/identity/composition`.

- **Tables:** `identity.user` (id, email, display name, created at) and `identity.sign_in_method` (user id, issuer, subject; primary key issuer + subject), migrations tracked in `migrations.identity` (ADR-004).
- **Global, not workspace-owned.** A person signs in before any workspace is chosen and can belong to several workspaces, so these tables have no `workspace_id` and no row-level security. The app role `aivera_app` gets select, insert, update and delete through the migrator's default privileges. Workspaces reach a user only by the opaque id in `workspaces.member.user_id`.
- **Email:** stored lower-case, enforced by the check `user_email_lower_case` and the unique `user_email_unique`. Plain `text` rather than `citext`, because `citext` must be allow-listed on Azure Database for PostgreSQL first (an infrastructure change).
- **Rules (`upsertUserFromIdToken`):** a known method returns its user. An unknown method needs a verified email: it then joins the user with that email or creates one. Verified means `email_verified: true`, or no claim at all from the app's own External ID tenant (`trustedIssuer`), which verifies every email before it creates an account (ADR-009 point 4, `isEmailVerified`). An explicit `false`, or another issuer without `true`, never creates or joins a user (`IdentityError('unverified_email')`, "Verify your email to continue."), so nobody can claim an address before its owner does. Every stored email is therefore verified, which is why there is no `email_verified` column. The display name follows the latest sign-in.
- **Tests:** `src/domain/user.test.ts`; database scenarios in `tests/integration/src/identity.test.ts`.
