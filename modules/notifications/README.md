# @credalent/notifications

The only place that sends email (AIV-P0-017). Candidates are contacted only when a person has confirmed something, so every email names the action that caused it. Other code imports only `@credalent/notifications` (the contract, `EmailQueuedV1`, `EmailError`); apps build it from `@credalent/notifications/composition`.

- **Queue (web app):** `createNotifications({ encryptionKey, origin, synthetic })` gives `queueEmail({ tx, workspaceId }, { template, to, data, causedBy, sender })`, called inside the confirmed action's workspace transaction. The web app builds it only where `OUTBOUND=on` (`apps/web/src/server/notifications.ts`); off, the default and the pilot's setting, it queues nothing and hides every send button (AIV-P1-165). It refuses before writing (`EmailError`): no `causedBy` ("Every email needs the action that caused it"), data that fails the template's zod schema (naming the fields), a bad address. It renders the template, seals the recipient, reply-to, subject and bodies with AES-256-GCM, and writes the `queued` row plus `EmailQueued.v1` (`{ messageId }`) to `notifications.outbox`. A rolled-back action queues nothing.
- **Send (worker):** `createEmailHandler({ encryptionKey, acs })` is the `notifications` queue's handler. It opens the row, POSTs to ACS (`Operation-Id` = row id, no open or click tracking), and marks the row `sent` with ACS's message id. A final refusal marks it `failed`; 429 and 5xx retry through the worker host. The worker never imports the JSX templates.
- **Delivery reports (web app):** `handleEventGrid(db, body)` answers Event Grid's handshake and moves a `queued` or `sent` row to `bounced` (Bounced, Suppressed) or `failed` (Failed, Quarantined, FilteredSpam). The route is `apps/web/src/app/api/webhooks/acs-email`, keyed by the Key Vault secret `acs-webhook-key`.
- **Tables:** `notifications.message` (id, workspace, template, `recipient_hash`, `sealed`, status `queued | sent | failed | bounced`, provider message id, `caused_by`, created and sent at), `notifications.outbox`, `notifications.inbox`. All `FORCE ROW LEVEL SECURITY` with the tenant policy.
- **The one exception to the tenant policy:** a delivery report knows only ACS's message id. `message_delivery_report_read` and `_mark` let `aivera_app` read and update exactly the row whose `provider_message_id` the transaction names in `app.provider_message_id`, which only `applyDeliveryReport` sets. The tenancy suite allows these two policies by exact expression.
- **Personal data (AGENTS.md 1.2):** the address, reply-to and bodies are only in `sealed`. Logs carry `notifications.recipient_hash` (HMAC-SHA256 with a key derived from the column key) and the row id. Subjects carry the job and the event, never a name.
- **Templates:** React Email components in `src/infrastructure/templates`, built from the artboards `ELayout`, `EComponents`, `EStyle`, `EEvidence`, and `EInvite` with its role variants `ERoles` (`member-invitation`, AIV-P1-003) (docs/01-design/artboards). The footer's reason follows the template (a candidate applied, or a member was invited); only candidate emails carry the delete-data link. Copy is in `packages/i18n` under `emails`; the plain text is written to match the artboard's. Dark colours ship in a `prefers-color-scheme` block, alignment follows the locale's direction, and the development band shows outside the pilot and production. A new email adds its data schema to `TEMPLATES` (domain) and its component to `render.ts`.
- **Not here:** evidence request content (AIV-P1-038), follow-ups (AIV-P1-040), a verified sender domain (AIV-P0-003 runbook).
- **Tests:** template and plain-text snapshot in `src/infrastructure/templates/render.test.ts` and `memberInvitation.test.ts`, sealing in `src/infrastructure/seal.test.ts`, scenarios in `tests/integration/src/notifications.test.ts`.
