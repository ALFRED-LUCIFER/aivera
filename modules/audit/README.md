# @credalent/audit

The append-only audit log (AIV-P0-013): who did what to which record, when and why. Score changes, rubric approvals, job creation, merges, decisions, assistant-confirmed actions and role changes write here (AGENTS.md 1.5, 3.6). Other code imports only `@credalent/audit` (the `AuditContract` types); apps build it with `createAudit(db, now)` from `@credalent/audit/composition`.

- **Table:** `audit.entry` (id, workspace id, `occurred_at` from the injected clock, `seq` (identity, insertion order), actor type and id, action, subject type and id, note, `before` and `after` as JSONB, correlation id). Migrations are tracked in `migrations.audit`; `audit` migrates first (ADR-004).
- **Writing in the caller's transaction:** `record({ tx, workspaceId, actor }, { action, subject, note, before, after })` inserts through the caller's own `withWorkspace` transaction, so the entry commits or rolls back with the change it records. Make it the last statement before commit.
- **Append-only, enforced by PostgreSQL, two layers** (migrations `0001_append_only`, `0002_always_triggers`):
  1. `REVOKE UPDATE, DELETE, TRUNCATE ON audit.entry FROM aivera_app`. `roles.sql` grants UPDATE and DELETE on every new table by default privilege, so the revoke is explicit. `aivera_app` gets `permission denied` (SQLSTATE 42501).
  2. Triggers `entry_append_only` (UPDATE, DELETE) and `entry_no_truncate` (TRUNCATE) call `audit.refuse_change()`, which raises `audit entries are append-only` (42501). While enabled they hold for every role, the owner included; they are `ENABLE ALWAYS`, so `session_replication_role = replica` does not skip them.
  - **Owner limit.** shortcut: the owner (`aivera_migrator`) can still disable or drop the triggers or drop the table; before the pilot, move ownership to a separate role or add an event trigger plus immutable backup.
- **Future audit tables:** a new table in `audit` repeats the REVOKE and both triggers on `audit.refuse_change()`, enabled `ALWAYS`, in its migration. An integration test checks every table in the `audit` schema for both and fails otherwise.
- **Order:** `listFor` returns entries by `occurred_at`, then `seq`, so entries written from one clock reading (a role change and the grant revocations it causes) read in the order they were written (AIV-P0-925).
- **Row-level security (ADR-005):** `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`; `listFor` also filters by workspace.
- **Rules:** `action` is one of the domain's `ACTIONS` (mirrored by a check constraint). `score.changed` and `decision.recorded` need a note ("A note is required for this action"), checked in the domain and by the `entry_note_check` constraint.
- **No candidate personal data (AGENTS.md 1.2):** actors and subjects are opaque ids. `before` and `after` are flat maps of ids, field names, enum values and numbers; `record` refuses any value that looks like an email address or phone number (so a plain date such as `2026-11-18` is refused too; pass a timestamp or epoch number), and `AuditError` never repeats the value. Keys are not checked. Names cannot be detected by pattern, so callers must not put them there (recorded as a `shortcut:` in `domain/entry.ts`). A note is a person's reason for a change and must not hold contact details.
- **Platform audit log (AIV-P2-035, [ADR-012](../../docs/adr/ADR-012-operator-console.md)):** `audit.platform_entry` (id, `occurred_at` from the injected clock, the operator's user id, action, optional subject type and id, note) records what Credalent operators did, outside any workspace: no workspace id, no tenant policy. `recordPlatform({ actorId, action, subject, note })` writes it in its own transaction; the actions so far are `ops.console_opened` and `ops.workspace_viewed` with the workspace as subject (AIV-P2-036) (`PLATFORM_ACTIONS`, mirrored by `platform_entry_action_check`). `aivera_app` may only insert: migration `0010_platform_entry_append_only` revokes `SELECT`, `UPDATE`, `DELETE` and `TRUNCATE`, and adds the same `ENABLE ALWAYS` append-only triggers as `audit.entry`. An operator action on a workspace is also written to that workspace's `audit.entry` with `record`, with actor type `operator` (AIV-P2-038). `ai_budget.changed` (AIV-P2-038) is on both lists, needs a note (`NOTE_REQUIRED`, and `entry_note_check` / `platform_entry_note_check`), and carries `before` and `after` (`platform_entry` gained both columns, checked for contact details as `record` does). `recordPlatform(entry, tx)` writes inside the caller's `withWorkspace` transaction when given one, so both entries commit or roll back with the change. `workspace.suspended` / `workspace.reactivated` (AIV-P2-037) are on both lists too, with the reason as note; the console lists a workspace's operator actions from its own log with `listOperatorEntries(workspaceId)` (operator entries about that workspace only, inside its scope), so the app still never reads the platform log. The console's audit page reads it through `listPlatformEntries({ action, actorId, targetId, from, to, cursor, pageSize })` (AIV-P2-053): zod-validated, newest first, at most 50 a page with a cursor (the id of the page's last entry; a full page always has one, so the page after it may be empty), through the `SECURITY DEFINER` function `audit.list_platform_entries` (migration `0021_list_platform_entries`). `aivera_app` may execute it and still has no privilege on the table. `recordPlatform` refuses `before` and `after` keys outside `PLATFORM_VALUE_KEYS`. Only console code may call it (architecture rule `platform-audit-read-console-only`). The catalogue editor's actions (`catalogue.draft_opened`, `catalogue.entry_added`, `catalogue.entry_edited`, `catalogue.entry_retired`, `catalogue.entry_removed`, `catalogue.draft_discarded`, `catalogue.eval_requested`, `catalogue.published`, [ADR-013](../../docs/adr/ADR-013-catalogue-in-the-database.md) point 14) are on the platform list since AIV-P2-043; the editor writes the first five since AIV-P2-045, with `catalogueVersion`, `publishedVersion`, `revision`, `entry`, `packKey` and `position` added to `PLATFORM_VALUE_KEYS`, `jobTypeKey` since AIV-P2-047, `region` for a regional hint since AIV-P2-046, and the change counts `added`, `edited` and `retired` of `catalogue.published` (with the reason as note) since AIV-P2-049, which also writes `catalogue.draft_discarded`.
- **Not here:** rendering an entry as a sentence ("12 Nov · Evidence assessed by Credalent…") belongs with the audit trail UI and its translations (AIV-P1-046, #110).
- **Tests:** domain rules in `src/domain/entry.test.ts`; database scenarios in `tests/integration/src/audit.test.ts` and `platform-audit-read.test.ts`.
