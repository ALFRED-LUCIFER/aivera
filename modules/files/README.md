# @credalent/files

Uploads straight from the browser to Blob storage, checked before and after (AIV-P0-016). Other code imports only `@credalent/files` (the `FilesContract` types, the limits and the events); apps build it with `createFiles({ db, workspaces, audit, blobs, malwareScanning })` and `createBlobStore({ url })` from `@credalent/files/composition`.

- **Table:** `files.file` (id, purpose `cv | evidence | portal | candidate_sheet`, content type, size, sha256, status `pending | clean | infected | rejected`, blob path, uploaded by, created at) and `files.outbox`. Exactly one owner (`file_one_owner_check`): a workspace (`workspace_id`), or for a candidate-site upload a candidate account (`candidate_account_id`, ADR-009). The file name as uploaded is stored for admins and recruiters to see (AIV-P1-165); blob names are `w/<workspace>/<file>` or `c/<account>/<file>`: opaque ids only (AGENTS.md 1.2). Migrations are tracked in `migrations.files`.
- **Limits** (`UPLOAD_LIMITS`, the CApply and Portal artboards): `cv` PDF or DOCX up to 10 MB ("PDF or Word, up to 10 MB."); `evidence` and `portal` PDF, PNG, JPEG, DOCX, PPTX or XLSX up to 20 MB ("PDF, image or document, up to 20 MB."); `candidate_sheet` CSV or XLSX up to 2 MB ("Use a CSV or Excel file up to 2 MB.", AIV-P1-103), kept in `cvs` once clean and read by the worker only. The extension and the declared type must agree. The messages are `files.limits.*` in `packages/i18n`; the browser checks first, the server again.
- **Upload:** `requestUpload(ctx, { purpose, fileName, contentType, size })` records a pending file (with its name as uploaded, AIV-P1-165: `fileNames(ctx, fileIds)` gives it to admins and recruiters to show in place of a candidate's name until one is read from the CV; never logged or put in a URL or blob path) and returns a SAS URL that may create that one blob in `uploads-quarantine`, once and never overwrite it, for 10 minutes: no read, no other blob (a user-delegation SAS; the account has shared keys off).
- **Scan, malware scanning on (pilot and production):** Defender for Storage scans each upload and Event Grid puts the result on the `malware-scan-results` queue; the worker calls `handleScanResult(body)`. "No threats found": the blob's size and stored content type are re-checked, it is copied to `cvs` (CVs) or `evidence`, hashed and marked `clean`, then removed from quarantine. "Malicious": deleted, `infected`. A blob that is not what was asked for: deleted, `rejected`. A settled file ignores a redelivered result.
- **Scan off (dev only):** `markCleanWithoutScan(ctx, id)`, called when the browser reports the upload done, settles it the same way without Defender. It throws `FileError('scanning_required')` wherever `malwareScanning` is on, and the web app refuses to start with `MALWARE_SCANNING=off` in the pilot or production. shortcut: malware scanning off in dev (synthetic data, owner decision 20 Nov 2026); the pilot sets MALWARE_SCANNING=on.
- **CV links from an imported sheet (AIV-P1-103):** `createCvLinkFetcher({ db, blobs, malwareScanning })` from the composition is the worker's fetch of one link: https only, no credentials, every resolved address checked against private, loopback, link-local, CGNAT, metadata and other non-public ranges before connecting, the connection pinned to the checked address, every redirect hop (at most 3) checked the same way, 10 s and 10 MB at most (`domain/fetchGuard.ts`, `infrastructure/cvFetch.ts`). A PDF or Word answer is stored as a pending `cv` file uploaded by the member who imported the sheet: its row commits first, then the blob lands in quarantine for Defender's scan, or is settled at once where scanning is off (dev). Anything else is null and stores nothing; no URL reaches a log or an error. shortcut: the guard copies the evidence link fetch's (AIV-P1-077), since files may not import evidence; merge them when either changes.
- **Opening a file (AIV-P1-045):** `issueReadLink(ctx, id)` returns a SAS URL that may read that one `clean` blob of the context's workspace for 5 minutes, served as an attachment (a user-delegation SAS); anything else is null, which the route `apps/web/src/app/api/files/[id]/link` answers with 404, and otherwise it redirects to the link. Every link issued is audited (`file.link_issued`: actor, time, file id) as the last statement. This is the only way a file leaves storage for a person: one short-lived, audited, read-only signed link, for admins and recruiters. Never a public blob URL. The earlier streamed download (`openDownload`, `/api/files/[id]`) had no caller and no audit entry, and is removed.
- **Authorisation:** through the workspaces `authorize`: `file.upload` (admins and recruiters) to upload and read one's own upload status; `file.download` is job-scoped with no job yet, so hiring owners and interviewers are refused until a file is reached through a candidate's job (AIV-P1-025).
- **Row-level security (ADR-005):** `ENABLE` + `FORCE ROW LEVEL SECURITY`; `tenantPolicy` on `workspace_id` and `candidateAccountPolicy` on `candidate_account_id` (OR-ed, and the owner check keeps them apart); the repository also filters by owner. The tenancy suite allows that one account policy on `files.file` only (`ACCOUNT_OWNED`).
- **Events:** `FileClean.v1` `{ fileId }` and `FileRejected.v1` `{ fileId, reason }`, written to `files.outbox` when a workspace's file settles. shortcut: the relay does not read `files.outbox` until something consumes them (CV parsing, AIV-P1-025); a candidate account's file has no workspace to publish to until the candidate site's apply flow (AIV-P3-008).
- **Not here:** the portal page (AIV-P1-041), the apply form (AIV-P3-008), parsing (AIV-P1-025, AIV-P1-028), and a `requestUpload` for a candidate account (AIV-P3-008).
- **Tests:** limits in `src/domain/files.test.ts`; the CV link guard in `src/domain/fetchGuard.test.ts` and `tests/integration/src/cv-link-fetch.test.ts`; use cases in `src/application/files.test.ts`; PostgreSQL and Azurite scenarios in `tests/integration/src/files.test.ts`.
