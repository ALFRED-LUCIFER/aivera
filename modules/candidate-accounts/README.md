# @aivera/candidate-accounts

The candidate's own side of Aivera (AIV-P3-006, ADR-009), separate from the recruiter-owned `@aivera/candidates` records. An account belongs to the person, not to a workspace: one per identity user, so one person can be both a recruiter and a candidate. Other code imports only `@aivera/candidate-accounts` (the `CandidateAccountsContract` types); apps build it with `createCandidateAccounts(db, now)` from `@aivera/candidate-accounts/composition`. **Recruiter-side modules never import it** (architecture rule `recruiter-side-no-candidate-accounts`), so nothing on the recruiter side can show that a recruiter is also a candidate.

- **Tables** (schema `candidate_accounts`, folder `modules/candidate-accounts`): `account` (primary key `identity_user_id`, the opaque identity user id, which is also the account id; full name and work type, set at sign-up in AIV-P3-007; no workspace id), `profile` (headline, location), `consent` (purpose `apply_to_job | answer_evidence_request | cv_check`, workspace id and job id, granted at, text version, withdrawn at) and `workspace_link` (workspace id, the workspace's candidate id, reason `applied | answered_evidence_request`, consent id; unique on account, workspace and candidate). Check constraints mirror the domain: a consent names a workspace and job exactly when it reaches one, and has a text version. The link's foreign key `(account_id, consent_id)` keeps a link on its own account's consent. Migrations are tracked in `migrations.candidate_accounts`.
- **Contract:** `withAccount(identityUserId, work)` opens a transaction scoped to the account and creates it on first use; `identityUserId` comes from the server-side candidate session only. Inside it: `getMyAccount`, `recordConsent`, `withdrawConsent` (stamps `withdrawn_at`, keeps the row; a second withdrawal is refused), `linkToWorkspace` (refused with `CandidateAccountError('consent_required')`, linking nothing, unless the consent is this account's, open, for that workspace and for the reason's purpose; linking again returns the existing link) and `listMyWorkspaceLinks` (for erasure, AIV-P3-014).
- **Row-level security (ADR-009):** every table `ENABLE` + `FORCE ROW LEVEL SECURITY` with `candidateAccountPolicy` on its account key, which reads `app.candidate_account_id` (set by `withCandidateAccount` in `@aivera/db`). The repository also filters by account. A transaction with no account set, including any recruiter workspace transaction, reads nothing here. The cross-workspace suite (`tests/integration/src/tenancy.test.ts`) checks these tables for the account policy instead of the workspace one (`ACCOUNT_TABLES`); a new table in the schema fails it until listed.
- **What a workspace receives:** only what the candidate submitted, through the recruiter-side modules. Never the account id or the profile; no recruiter-side table has a column for them (integration-tested).
- **Personal data (AGENTS.md 1.2):** full name, headline and location (`PERSONAL_DATA_FIELDS`). The module never logs; `CandidateAccountError` carries no personal data.
- **Audit:** not written here. `audit.entry` is workspace-scoped (row-level security on `app.workspace_id`) and has no candidate actor; the consent row itself is the record (never deleted on withdrawal).
- **Not here:** sign-up and sign-in screens (AIV-P3-007), applying (AIV-P3-008, which checks the job is published before recording consent), answering evidence requests (AIV-P3-013), erasure (AIV-P3-014). The `application.consent_withdrawn` event is published from `withdrawConsent` once the outbox lands (AIV-P0-014); until then the withdrawal is recorded only.
- **Tests:** consent and link rules in `src/domain/account.test.ts`; database scenarios in `tests/integration/src/candidate-accounts.test.ts`.
