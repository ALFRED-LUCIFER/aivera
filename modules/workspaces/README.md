# @aivera/workspaces

The tenancy module (AIV-P0-008). A workspace is one hiring team; members belong to it with a role (`admin`, `recruiter`, `hiring_owner`, `interviewer`) and a status (`invited`, `active`, `removed`). Other code imports only `@aivera/workspaces` (the `WorkspacesContract` types); apps build it with `createWorkspaces(db, audit)` from `@aivera/workspaces/composition`.

- **Tables:** `workspaces.workspace` (with `type`: `in_house` or `agency`, default `in_house`, and `ai_daily_token_budget`, AIV-P2-038), `workspaces.member` (primary key `(workspace_id, user_id)`), `workspaces.client`, `workspaces.job_grant`, `workspaces.ai_token_usage` and `workspaces.settings`, migrations tracked in `migrations.workspaces` (ADR-004).
- **Row-level security (ADR-005):** the six workspace-owned tables have `ENABLE` + `FORCE ROW LEVEL SECURITY` and `tenantPolicy` from `@aivera/db/tenant-policy`.
- **Decision: `workspaces.workspace` is keyed on its own `id`.** Inside `withWorkspace(W)` only workspace W is visible, so a member reads only a workspace whose scoped transaction the request context opened for them. `createWorkspace` generates the id, opens `withWorkspace` on it and inserts the workspace and its first admin in one transaction, so no bypass role is needed.
- **Rules:** only an active admin changes roles; the last active admin cannot stop being one ("A workspace needs at least one admin"). `changeRole` locks the workspace's member rows (`FOR UPDATE`), so two concurrent changes cannot both remove an admin. Each role change appends a `member.role_changed` entry (before and after role) to `@aivera/audit` in the same transaction; `createWorkspace` appends `workspace.created` by the creator the same way (AIV-P1-001).
- **Request context (AIV-P0-010):** `withWorkspace(session, workspaceId, fn)` checks, inside the workspace's scoped transaction, that the user is an active member, then calls `fn({ userId, workspaceId, role, tx })`; anyone else gets `ForbiddenError` and `fn` never runs. Module repositories take that `tx`, never the pool (architecture test `scoped-tx-only`). `authorize(ctx, action, resource?)` reads the permission map in `src/domain/permissions.ts`: each action lists its roles and is workspace-wide or job-scoped. A job-scoped action for a hiring owner or interviewer also needs a `resource` (`{ jobId, clientId }`) and a covering grant from the `JobGrants` port, which reads the member's grants in `ctx.tx` (`grantsCover` in `src/domain/permissions.ts`). `withWorkspace` also sets `app.job_scope` (`all` for admins and recruiters, `granted` otherwise), `app.job_ids` and `app.client_ids` (uuid array literals such as `{…}`) transaction-locally, for the job-scope policy on tables that carry a job and client id (ADR-005 point 6; the first is `jobs.job`, AIV-P1-005).
- **Agency clients and job grants (AIV-P0-906, ADR-009):** an admin sets the workspace type (`setWorkspaceType`; an agency with clients that are not archived cannot become in-house). Admins and recruiters of an agency add, rename and archive clients; names are unique per workspace in any letter case (unique index on `lower(name)`). Admins grant a hiring owner or interviewer one job (`jobId`, an opaque jobs-module id) or all of one client's jobs, current and future (`clientId`); a check constraint makes exactly one set, and keys on `(workspace_id, user_id)` and `(workspace_id, client_id)` stop a grant naming another workspace's member or client. Every write appends an audit entry (`workspace.type_changed`, `client.added`/`renamed`/`archived`, `job_access.granted`/`revoked` on the member). Changing a member to admin or recruiter deletes their grants; changing back starts with none. A revoked grant stops working on the member's next request.
- **Decision: the active workspace is a pointer table, `workspaces.active_workspace`** (user id, workspace id), not a cross-workspace read of `member` (ADR-005 point 2). It is keyed on the user and has no tenant policy: it is read before any workspace is open and holds two opaque ids. Nothing trusts it: every request re-checks membership, and `switchWorkspace` refuses (and keeps the current one) when the user is not an active member of the target. A user with no row has no workspace yet; listing a user's workspaces for the switcher (AIV-P1-055) still needs the named policy.
- **Daily AI token use (AIV-P0-033, ADR-006 point 2):** `workspaces.ai_token_usage` holds one row per workspace and UTC day (`tokens` bigint, `CHECK (tokens >= 0)`, primary key `(workspace_id, usage_day)`, tenant policy and FORCE). `createAiTokenBudget(db)` from `@aivera/workspaces/composition` is the `AiTokenBudget` store apps pass to `@aivera/ai`'s `createAiClient({ budget })`: `spentToday` reads the day's row, `add` is one `INSERT … ON CONFLICT DO UPDATE SET tokens = tokens + excluded.tokens`, so concurrent calls from every process never lose an increment. Each call runs in the workspace's scoped transaction. The synthetic purge deletes the rows with the workspace.
- **Per-workspace AI budget (AIV-P2-038, ADR-006 point 2, ADR-012):** `spentToday` returns `{ spent, limit }` in one statement: the day's tokens and the budget in force, `workspaces.workspace.ai_daily_token_budget` (null: `AI_DAILY_TOKEN_BUDGET.default`, 2,000,000; otherwise 100,000 to 10,000,000, `workspace_ai_daily_token_budget_check`). `createAiBudgetConsole(db, audit)` is the `AiBudgetConsole` contract for `/ops` only: `usage(workspaceId, today, days)` (the budget and each of the last `days` UTC days, newest first, 0 for a day with no call) and `setDailyBudget({ operatorId, workspaceId, dailyBudget, reason })`, which locks the workspace row (`FOR UPDATE`, so concurrent changes record a true "before"), sets the override (null resets it) and records `ai_budget.changed` (before and after budget, reason) in the platform audit log and, last, the workspace's audit log with actor `operator`, all in one `withWorkspace(<that workspace>)` transaction.
- **Operator console reads (AIV-P2-036, [ADR-012](../../docs/adr/ADR-012-operator-console.md) point 6):** `createWorkspaceDirectory(db)` from `@aivera/workspaces/composition` is the `WorkspaceDirectory` contract for `/ops` only: `listSummaries({ query, offset, limit })` (name contains `query` in any case, newest first, with the match count) and `getSummary(workspaceId)`. A `WorkspaceSummary` holds id, name, type, created date, synthetic flag, status (`active` or `suspended`) and the active member count: never a member, a client or candidate data. The list comes from `workspaces.directory` (workspace id and created date only, no tenant policy, like `active_workspace`; written by `insertWorkspace` in `createWorkspace`'s transaction and deleted by `deleteWorkspace`; migration `0008_directory_backfill` lists the workspaces that existed before it, from `active_workspace`). Each workspace is then read inside `withWorkspace(<that workspace>)` as `aivera_app`, under its unchanged tenant policies. shortcut: one transaction per workspace and the name match in memory; the `aivera_ops` role is the upgrade when the list is slow.
- **Status (AIV-P2-037, AIV-P2-039, ADR-012 point 7):** `workspaces.workspace.status` is `active`, `suspended`, `pending_approval` or `rejected` (`workspace_status_check`). `createWorkspace({ …, needsApproval })` starts a sign-up's workspace `pending_approval` (the web sign-up passes the `ops` switch; the seed and tests leave it out: active). `STATUS_CHANGES` lists what an operator may do: suspend and reactivate, and approve (no reason) or reject (a reason) a pending workspace; `WorkspaceDirectory.listPending()` lists the waiting ones oldest first with their creator's opaque user id. `changeStatus({ operatorId, workspaceId, change, reason }, alongside?)` is for the operator console only (the caller checks `platformOperator`; architecture rule `operator-only-writes`): inside `withWorkspace(<the workspace>)` as `aivera_app` it locks the row `FOR UPDATE`, refuses a stale change (`status_conflict`) or a reason under 10 characters (`reason_required`), writes the status, runs `alongside(tx)` (the app hides the workspace's public jobs there through `jobs.pausePublicListings`), then audits last: `workspace.suspended`, `workspace.reactivated`, `workspace.approved` or `workspace.rejected` in the workspace's `audit.entry` with actor `operator`, and the same action in `audit.platform_entry`, in that one transaction. `withWorkspace` reads the status into the context under `FOR KEY SHARE` (held to commit, so a suspension waits for work in flight), and `authorize` refuses every action not marked `reads: true` in `PERMISSIONS` with `WorkspacePausedError` (a `ForbiddenError`, so HTTP 403) while the workspace is not active. Reads stay open; nothing is deleted, hidden or reordered. shortcut: there is no worker, AI call or outbound email yet, so nothing else to stop; the worker job wrapper (when `apps/worker` exists) must check `ctx.status` the same way, and AI calls and emails run inside an authorised action.
- **Workspace settings (AIV-P1-051):** `src/domain/settings.ts` is the one source of the approved defaults and bounds (`SETTING_BOUNDS`, `DEFAULT_SETTINGS`, `settingsSchema`, `settingsPatchSchema`; the settings screen reuses them through the contracts). `workspaces.settings` holds one `jsonb` value per workspace (primary key `workspace_id`, `updated_at`, `updated_by`, tenant policy and FORCE), written on the first change; no row means every default. `getSettings(ctx)` (every member) returns the stored values over the defaults, a value no longer allowed falling back to its default. `updateSettings(ctx, patch)` is admin-only (`workspace.settings`), refuses the whole patch with `SettingsError` ("sessionIdleHours must be between 1 and 12") before writing anything, locks the workspace row so concurrent changes record a true "before", and audits `workspace.settings_changed` with each changed key's old and new value, last. Values are read at call time, so a change applies to what is issued after it; each consuming ticket stores the expiry it issued with.
