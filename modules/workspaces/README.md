# @aivera/workspaces

The tenancy module (AIV-P0-008). A workspace is one hiring team; members belong to it with a role (`admin`, `recruiter`, `hiring_owner`, `interviewer`) and a status (`invited`, `active`, `removed`). Other code imports only `@aivera/workspaces` (the `WorkspacesContract` types); apps build it with `createWorkspaces(db, audit)` from `@aivera/workspaces/composition`.

- **Tables:** `workspaces.workspace` and `workspaces.member` (primary key `(workspace_id, user_id)`), migrations tracked in `migrations.workspaces` (ADR-004).
- **Row-level security (ADR-005):** both tables have `ENABLE` + `FORCE ROW LEVEL SECURITY` and `tenantPolicy` from `@aivera/db/tenant-policy`.
- **Decision: `workspaces.workspace` is keyed on its own `id`.** Inside `withWorkspace(W)` only workspace W is visible, so a member reads only a workspace whose scoped transaction the request context opened for them. `createWorkspace` generates the id, opens `withWorkspace` on it and inserts the workspace and its first admin in one transaction, so no bypass role is needed.
- **Rules:** only an active admin changes roles; the last active admin cannot stop being one ("A workspace needs at least one admin"). `changeRole` locks the workspace's member rows (`FOR UPDATE`), so two concurrent changes cannot both remove an admin. Each role change appends a `member.role_changed` entry (before and after role) to `@aivera/audit` in the same transaction.
- **Request context (AIV-P0-010):** `withWorkspace(session, workspaceId, fn)` checks, inside the workspace's scoped transaction, that the user is an active member, then calls `fn({ userId, workspaceId, role, tx })`; anyone else gets `ForbiddenError` and `fn` never runs. Module repositories take that `tx`, never the pool (architecture test `scoped-tx-only`). `authorize(ctx, action, resource?)` reads the permission map in `src/domain/permissions.ts`: each action lists its roles and is workspace-wide or job-scoped. A job-scoped action for a hiring owner or interviewer also needs a `resource` (`{ jobId, clientId }`) and a covering grant from the `JobGrants` port; until AIV-P0-906 that port covers nothing, so those roles are refused every job-scoped action.
- **Decision: the active workspace is a pointer table, `workspaces.active_workspace`** (user id, workspace id), not a cross-workspace read of `member` (ADR-005 point 2). It is keyed on the user and has no tenant policy: it is read before any workspace is open and holds two opaque ids. Nothing trusts it: every request re-checks membership, and `switchWorkspace` refuses (and keeps the current one) when the user is not an active member of the target. A user with no row has no workspace yet; listing a user's workspaces for the switcher (AIV-P1-055) still needs the named policy.
- **Tests:** domain rules in `src/domain/workspace.test.ts`, the permission matrix in `src/application/context.test.ts`; database scenarios in `tests/integration/src/workspaces.test.ts`.
