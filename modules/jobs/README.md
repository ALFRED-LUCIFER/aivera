# @aivera/jobs

Jobs and their own versioned rubrics (AIV-P1-005), and the job types catalogue (AIV-P1-004). Every job has its own rubric; editing an approved rubric starts a new version that needs approval, and the approved version stays in force until then. Assessment reads only the approved version. Other code imports only `@aivera/jobs` (the `JobsContract` types); apps build it with `createJobs(workspaces, audit, now)` from `@aivera/jobs/composition`.

- **Job types:** `JOB_TYPE_CATALOGUE` in `src/domain/job-types.ts` lists the ten job types in PRODUCT.md's order. Each has a `key`, a `labelKey` and an `evidenceKey` (`jobTypes.<key>.*` in `packages/i18n`), and four starter competencies. It is code, reviewed in PRs, with no table. Bump `JOB_TYPE_CATALOGUE_VERSION` when an entry changes meaning. Keys are stored as a workspace's hiring focus and a job's type, so a key is never renamed.
- **Tables (schema `jobs`, tracked in `migrations.jobs`):** `job` (title, job type, description, team, client id, location, hiring owner user id, stage, published, public descriptor (how the candidate site names the employer, never the client's name), published at, pay band in integer minor units plus currency, `synthetic`, created by and at); `rubric_version` (job, version number, status `draft | awaiting_approval | approved | superseded | returned`, success statement, change note, created by and at, approved by and at); `competency` (version, name, evidence expected, weight percent, level needed, type `mandatory | desirable`, origin `from_description | suggested_by_aivera`, position). The client and hiring owner are opaque ids of the workspaces module (no foreign key across modules); child rows are keyed with the workspace, so they cannot point into another workspace.
- **Rules, in the domain and in the database (AGENTS.md 3.5):** weights in a version total 100 (`assertValidCompetencies`, and a deferred constraint trigger `competency_weights_total_check` at commit); each weight 1–100 and level 1–5 (check constraints); at most one approved version per job (partial unique index `rubric_version_one_approved_idx`); approving supersedes the previous approved version in the same transaction, under a lock on the job row; an approved or superseded version and its competencies never change (triggers `rubric_version_frozen_check`, `competency_version_frozen_check`).
- **Contract:** `getJob`, `listJobs`, `getApprovedRubric(jobId)` (null when none is approved), and `createJob`, `saveRubric`, `submitRubric`, `approveRubric`, and for the candidate site `getPublicListing(jobId)` (the allow-listed listing for the publish preview: title, job type, descriptor, location, pay band, competencies with evidence expected and level; no weight, client, description or ids), `publishJob(jobId, { publicDescriptor })` (needs an approved rubric) and `unpublishJob(jobId)`, both audited. Each takes the request context from `WorkspacesContract.withWorkspace` and runs in its scoped transaction. Rule failures throw `JobError`; refusals `ForbiddenError`.
- **Authorisation:** through the workspaces `authorize`: `job.create` and `rubric.edit` for admins and recruiters, `rubric.approve` for admins and the job's granted hiring owner, `job.view` (job-scoped) and `job.list` for every role.
- **Row-level security (ADR-005):** all three tables `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`. Job scope (point 6): `job` has the restrictive policy `job_scope` (`app.job_scope = 'all'`, or the job id is in `app.job_ids`, or its client id in `app.client_ids`), and `rubric_version` and `competency` have restrictive policies that require their job (through the version) to be visible, so a hiring owner or interviewer cannot read another job's rubric either. The repository filters by the workspace and by the same job-scope expression (`jobInScope`).
- **Audit:** `job.created` and `rubric.approved` (actor, time, before and after) are written last in the transaction (AGENTS.md 3.6).
- **Events:** `RubricApproved.v1`, `JobPublished.v1` and `JobUnpublished.v1` (opaque ids only) are defined in the contract and written from `approveRubric`, `publishJob` and `unpublishJob` once the outbox lands (AIV-P0-014).
- **Not here:** returning a version and approval notifications (AIV-P1-014), screens (AIV-P1-006, AIV-P1-007, AIV-P1-012) including the rubric-page Publish panel (AIV-P1-015), the public read model (AIV-P3-002), the demo seed's five jobs (AIV-P0-031; they live in the integration test fixture until then).
- **Tests:** rules in `src/domain/job.test.ts`; the catalogue in `src/domain/job-types.test.ts`; database scenarios in `tests/integration/src/jobs.test.ts`.
