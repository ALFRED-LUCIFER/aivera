# @credalent/intake

Applications per job and where each one came from (AIV-P1-017). An application links one person (`@credalent/candidates`) to one job (`@credalent/jobs`). Other code imports only `@credalent/intake` (the `IntakeContract` types); apps build it with `createIntake(workspaces, candidates, jobs, displayNamesInWorkspace, now)` from `@credalent/intake/composition`, where `displayNamesInWorkspace` is the candidates composition's unauthorised names read (AIV-P1-086), called only after `listApplicationsForJob` has authorised the job.

- **Tables:** `intake.application` (person id, job id, stage, `received_at` of the first arrival, `submitted_to_client_at`), `intake.application_source` (one row per arrival: source, `received_at`, Blob `file_ids`, `links`, the candidate-supplied `github_login`) and `intake.outbox`. `application_person_job_key` makes one application per person per job, so a second arrival adds a source. Person and job ids are opaque: no foreign keys across modules. The source's foreign key includes the workspace, so it cannot point at another workspace's application. Migrations are tracked in `migrations.intake`.
- **Sources:** `linkedin | careers_page | referral | email | whatsapp | recruiter` (a link a member added), a check constraint matching `SOURCES`.
- **Stages:** `new | first_pass_done | assessing | in_process | in_pool | withdrawn`, a check constraint matching `STAGES`. There is no rejected stage: nothing rejects a candidate automatically (AGENTS.md 1.5).
- **Contract:** `receiveApplication(ctx, { jobId, person, source, fileIds, links, githubLogin })` checks the job is in the workspace (else `IntakeError('job_not_found')`, writing nothing), finds or creates the person, creates or reuses the application and records the source. Admins and recruiters (`candidate.create`). `addLink(ctx, applicationId, url)` (AIV-P1-076) records a member's link as a `recruiter` source: the job comes from the stored application, and `application.add_link` allows admins and recruiters, and hiring owners and interviewers only on that job (a grant on it or its client); anyone else gets `ForbiddenError` and nothing is written. Every link stays on the application; evidence reads the GitHub repository ones. `listApplicationsForJob(ctx, jobId)` (AIV-P1-086) lists the job's applicants, newest first, with their display name, stage, received date and first source; a job the context cannot see (another workspace's, or not granted to a hiring owner or interviewer) is `IntakeError('job_not_found')`.
- **System read:** `readApplicationSourceAsSystem(tx, workspaceId, sourceId)` from the composition gives an arrival's person, links and login to the evidence module's `ApplicationReceived.v1` handler (a worker job with no member).
- **Event:** `ApplicationReceived.v1` (`{ applicationId, sourceId }`, strict, opaque ids only) is written to `intake.outbox` in the same transaction, on every arrival (each can bring new files) and every member's link. The worker relays it to the `evidence` queue.
- **Row-level security (ADR-005):** every table `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`; the repository also filters by workspace.
- **Personal data (AGENTS.md 1.2):** `links` and `githubLogin` are personal data (`PERSONAL_DATA_FIELDS`); the module never logs.
- **Not here:** merging duplicate people (AIV-P1-018), the email and upload channels and their zod validation (AIV-P1-019), careers-page applications from the candidate site (AIV-P3-008).
- **Tests:** stage enum in `src/domain/application.test.ts`; database scenarios in `tests/integration/src/intake.test.ts`.
