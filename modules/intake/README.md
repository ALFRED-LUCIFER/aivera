# @credalent/intake

Applications per job and where each one came from (AIV-P1-017). An application links one person (`@credalent/candidates`) to one job (`@credalent/jobs`). Other code imports only `@credalent/intake` (the `IntakeContract` types); apps build it with `createIntake(workspaces, candidates, jobs, displayNamesInWorkspace, audit, now)` from `@credalent/intake/composition`, where `displayNamesInWorkspace` is the candidates composition's unauthorised names read (AIV-P1-086), called only after `listApplicationsForJob` has authorised the job.

- **Tables:** `intake.application` (person id, job id, stage, `received_at` of the first arrival, `submitted_to_client_at`), `intake.application_source` (one row per arrival: source, `received_at`, Blob `file_ids`, `links`, the candidate-supplied `github_login`), `intake.import_batches` (one confirmation per save of "Add applicants": job, who, when, wording key and version, `cvs` the number of CVs added, not distinct people; each source carries its `batch_id`, AIV-P1-104), `intake.sheet_imports` (a CSV or Excel import in progress, AIV-P1-103), `intake.outbox` and `intake.inbox` (AIV-P2-012). `application_person_job_key` makes one application per person per job, so a second arrival adds a source. Person and job ids are opaque: no foreign keys across modules. The source's foreign key includes the workspace, so it cannot point at another workspace's application. Migrations are tracked in `migrations.intake`.
- **Sources:** `linkedin | careers_page | referral | email | whatsapp | recruiter` (a link a member added) `| spreadsheet` (a row of an imported sheet, AIV-P1-103), a check constraint matching `SOURCES`.
- **Stages:** `new | first_pass_done | assessing | interview | in_process | in_pool | withdrawn | round2_shortlist | not_advanced`, a check constraint matching `STAGES`. There is no rejected stage: nothing rejects a candidate automatically (AGENTS.md 1.5).
- **Choose for interview (AIV-P1-114):** `chooseForInterview(ctx, { jobId, applicationIds, reason })` moves each application to `interview` and creates its Round 1 interview (structured screen, the member as interviewer, the candidate's evidence gaps to investigate, no time yet) through the interviews contract, then audits one `application.stage_changed` per person (from and to stage, job, interview id, the reason as note) last, in one transaction. Someone already at `interview` is skipped, and so is someone the hiring owner put on the Round 2 shortlist or did not advance (`chosenOrDecided`, AIV-P2-012): a new choice would reverse a recorded decision, and the ranking's preview says why each is not chosen; an application of another job refuses the whole choice (`IntakeError('not_on_job')`); an empty reason is `reason_required`. Admins and recruiters on the job (`interview.schedule`). Nobody is contacted. The interviews and assessment calls are ports (`InterviewPorts`) an app passes to `createIntake`, so intake has no package edge to either; without them the command throws.
- **Contract:** `receiveApplication(ctx, { jobId, person, source, fileIds, links, githubLogin })` checks the job is in the workspace (else `IntakeError('job_not_found')`, writing nothing), finds or creates the person, creates or reuses the application and records the source. Admins and recruiters (`candidate.create`). `addLink(ctx, applicationId, url)` (AIV-P1-076) records a member's link as a `recruiter` source: the job comes from the stored application, and `application.add_link` allows admins and recruiters, and hiring owners and interviewers only on that job (a grant on it or its client); anyone else gets `ForbiddenError` and nothing is written. Every link stays on the application; evidence reads the GitHub repository ones. `listApplicationsForJob(ctx, jobId)` (AIV-P1-086) lists the job's applicants, newest first, with their person id (the ranked table's join key, AIV-P1-034), display name, stage, received date and first source; a job the context cannot see (another workspace's, or not granted to a hiring owner or interviewer) is `IntakeError('job_not_found')`. `countApplications(ctx, jobId)` (AIV-P1-101) counts the job's applications from every source, with the same access.
- **Batches (AIV-P1-104):** `receiveBatch(ctx, { jobId, rightToProcessConfirmed: true, wordingKey, arrivals })` refuses unless the recruiter confirmed (`IntakeError('confirmation_required')`), stores the batch, receives every arrival under it and audits `intake.batch_confirmed` last. `addLink` inherits the application's batch. `receiveApplication` stores no batch, and the worker never reads such an arrival; applications from before the batches have none either (shortcut: no backfill, links added to them are stored but not read).
- **Sheet imports (AIV-P1-103):** `startSheetImport(ctx, { jobId, fileId })` (the web action first checks the file is the member's own clean `candidate_sheet` upload) stores the import as `reading` and writes `SheetImportRequested.v1` (`{ sheetImportId }`, strict). The worker's `createSheetImportHandler({ readCleanFile, fetchCv })` (both from the files composition, so intake has no package edge to files) reads the first sheet (`read-excel-file` for `.xlsx`, `parseCsv` for UTF-8 or Windows-1252 CSV) and stores its header row (`mapping`), or marks it `unreadable` (not readable, or over 1,000 rows). `getSheetImport` shows the header row and the mapping `proposeMapping` suggests ("Full name", "E-mail", "Resume URL"). `confirmSheetMapping` stores the recruiter's mapping (every column in the header row, Name and Email set, none twice, else `invalid_mapping`) as `fetching` and writes the event again: the worker reads the rows (`readRows`: a row with no name, no email or an email the candidates module would refuse is kept as its row number and problem only), fetches each CV link through the files module's SSRF guard into quarantine as the member's `cv` upload, and marks it `ready`. `addSheetImport` (after the right-to-process tick) moves it to `added` and adds every usable row through `receiveBatch` with source `spreadsheet`, audited `intake.batch_confirmed` last; a CV still waiting for its scan is linked and read once clean, as for an upload. Each import is its starter's (`sheet_not_found` for anyone else); each step runs once (`sheet_not_ready` otherwise). `headers` and `rows` are the sheet's values: never logged, thrown or put in a URL. shortcut: duplicate merging and the "already submitted to this client" check before adding are AIV-P1-102.
- **Decision stages (AIV-P2-012):** `createDecisionStageHandler({ event, decisionsOf, audit })` from the composition is the worker's job for the decisions module's `DecisionsRecorded.v1`, once per message id (`intake.inbox`, row-level security forced): each decided candidate's application on the pack's job moves to `round2_shortlist` (advance) or `not_advanced` (do not advance); a hold, an application already there, a withdrawn one or none is left alone. Each move is audited `application.stage_changed` with the hiring owner as actor, their reason as note and `{ stage, jobId, packId }`, after all the moves. The event and `decisionsOf` (`readDecisionsAsSystem`) come from the worker, so intake has no package edge to decisions (which reaches intake through evidence). Nobody is contacted; a not advanced candidate stays in the ranking and can join a later pack.
- **System read:** `readApplicationSourceAsSystem(tx, workspaceId, sourceId)` from the composition gives an arrival's person, links and login to the evidence module's `ApplicationReceived.v1` handler (a worker job with no member).
- **Event:** `ApplicationReceived.v1` (`{ applicationId, sourceId }`, strict, opaque ids only) is written to `intake.outbox` in the same transaction, on every arrival (each can bring new files) and every member's link. The worker relays it to the `evidence` queue.
- **Row-level security (ADR-005):** every table `ENABLE` + `FORCE ROW LEVEL SECURITY` with `tenantPolicy` on `workspace_id`; the repository also filters by workspace.
- **Personal data (AGENTS.md 1.2):** `links` and `githubLogin` are personal data (`PERSONAL_DATA_FIELDS`); the module never logs.
- **Duplicate merge (AIV-P1-018):** `applicationRecords` from the composition (unauthorised; apps wire it into `createCandidates`, whose merge authorises) lists, moves and restores a person's applications. When both people applied to the same job, the merged person's sources join the survivor's application and their emptied application is kept for the undo; `jobsForCandidate`, `candidatesForJob` and `listApplicationsForJob` skip an application with no source.
- **Not here:** the email and upload channels and their zod validation (AIV-P1-019), careers-page applications from the candidate site (AIV-P3-008).
- **Tests:** stage enum in `src/domain/application.test.ts`; choose rules in `src/application/applications.test.ts`; decision stages in `src/application/decisions.test.ts` and `tests/integration/src/record-decisions.test.ts`; database scenarios in `tests/integration/src/intake.test.ts` and `tests/integration/src/choose-for-interview.test.ts`; sheet imports in `src/domain/sheet.test.ts`, `tests/integration/src/sheet-import.test.ts` and `tests/e2e/src/sheet-import.spec.ts`.
- **Demo seed:** `purgeSyntheticApplications(ctx)` is the reset of `pnpm db:seed --reset`: it deletes the workspace's applications, sources, batches and sheet imports. Admins, and only in a workspace flagged synthetic (`IntakeError('not_synthetic')` otherwise, deleting nothing). The seed's applications carry no batch, so the worker never reads them.
